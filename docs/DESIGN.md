# 設計方針

このドキュメントは現状の設計を常に表す「生きたドキュメント」です。
バージョン名(v9・v10等)では管理せず、変更があればこのファイル自体を上書き更新します。
個々の変更の経緯を残したい場合はコミットメッセージ側に記録してください。

## データ構造

| データ | テーブル | 備考 |
|---|---|---|
| 通常購入 | `tickets` | 購入グループ`group_id` + 組み合わせ1点=1行 |
| CSV原本(Club JRA-Net等) | `imported_tickets` | 外部CSVの原本をそのまま保持 |
| CSV購入グループ | `imported_ticket_groups` | CSVの1行=1購入グループ |
| CSV個別買い目 | `imported_ticket_items` | 組み合わせを個別買い目へ分解したもの |
| 予想印 | `prediction_marks` | **1頭につき1つまで**(2026-07-30〜。ドロップダウン選択式に変更。以前は複数登録可能だった)。印の種類: ◎○▲△☆消。2026-08-01よりユーザーごとに分離(`UNIQUE(race_id, horse_number, user_id)`)。**`horse_number`はNOT NULL制約があるため、枠番・馬番が未確定の馬には印を付けられない(下記「出走馬一覧PDFインポート」参照)** |
| 予想メモ | `prediction_notes` | レース単位の自由記述メモ(`prediction.html`)。2026-08-01よりユーザーごとに分離(`UNIQUE(race_id, user_id)`) |
| 馬メモ | `horse_notes` | 馬名をキーに継続管理。馬名はtrim/空白正規化して保存。2026-08-01よりユーザーごとに分離(`UNIQUE(horse_name, user_id)`)。**馬名がキーのため、枠番・馬番の有無に関係なく常に利用できる** |
| ユーザーアカウント | `users` | 2026-08-01追加。ログイン画面から自己登録できる(招待コード等の制限なし) |

### レース情報のコース種別・距離(2026-08-02〜)

`races`テーブルに`course_type`(TEXT)・`distance`(INTEGER)を追加した。

- `course_type`: `芝`/`ダート`/`障害`のいずれか。**任意入力**(NULL可)。
  一覧・カード等での表示時は`芝`→`芝`、`ダート`→`ダ`、`障害`→`障`と
  1〜2文字に短縮して表示する(表示ロジック側の変換であり、保存値そのものは
  フルの日本語表記のまま)
- `distance`: メートル単位の整数。**任意入力**(NULL可)。半角数字のみ
- 両カラムとも既存レース(移行前に登録済みのレース)は`NULL`のままでよい。
  後から編集画面で追記できる
- 集計等でコース情報が無いレースを扱う場合は、フォールバックとして
  競馬場(`track`)単位の扱いにする(コース別収支タスクで対応予定)

### 出走馬(`races.entries`)の枠番・馬番のnullable化(2026-08-07〜)

出走馬一覧PDFインポート(下記参照)対応により、`races.entries`(JSON配列)内の
各出走馬オブジェクトの`waku_number`・`horse_number`が**null になりうる**ように
なった(枠番・馬番の抽選前に登録するケースに対応するため)。

- `entries`はスキーマレスなJSON列(`entries TEXT NOT NULL`)のため、この変更に
  DBマイグレーションは不要
- 馬の同一性は、`horse_number`ではなく**`horse_name`(馬名)をキー**に判定する
  (未確定時は馬名しか手がかりがないため。`horse_notes`が既に馬名をキーにして
  いるのと同じ考え方)
- `horse_number`がnullの馬が1頭でも含まれるレースは、以下のように扱われる:
  - **購入(`buy.js`)**: 選択・購入できない(「枠番・馬番が未確定のため購入できません」
    という案内を表示してブロックする)
  - **予想印(`prediction.js`)**: その馬の予想印セレクトは無効化される(`prediction_marks`が
    `horse_number NOT NULL`のため、そもそも保存できない)。一覧の並び順は、
    馬番が無い馬がいる場合は馬名(五十音)順にフォールバックする
  - **馬メモ(`horse_notes`)**: 馬名がキーのため、通常通り利用できる(制限なし)
  - **レース管理画面(`races.js`)**: 出走馬登録状況バッジに「(枠番未確定)」の表示が付く
  - **枠連(wakuren)の払戻判定(2026-08-09〜)**: `waku_number`が未確定の出走馬が
    絡む枠連馬券は、的中組み合わせ自体を算出できないため「不的中(0円)」と断定せず
    「判定不能(未確定のまま)」として扱う。詳細は下記「払戻確定時のticket反映」参照

## 出走馬一覧PDFインポート(枠番なし/あり統合・2026-08-07〜)

JRA公式サイトの「出走馬一覧」PDF(1開催日・1ファイルにつき12レース分)を解析し、
出走馬(馬名・騎手・枠番・馬番)を一括登録・更新する機能。管理者専用。

### 想定する運用フロー

```
月・火・水: 開催日程を手動登録(既存の「開催日程を一括登録」)
木        : 出走馬一覧(枠番・馬番未確定)PDFをインポート ← 本機能
金        : 出走馬一覧(枠番・馬番確定後)PDFを同じ機能で再インポート ← 本機能
土・日     : 払戻一覧PDFをインポート(既存の「JRAレース結果PDFをインポート」)
```

木(枠番なし)・金(枠番あり)は**同じ機能・同じボタン**で対応する。PDFのフォーマットは
枠番・馬番列が埋まっているかどうかだけの違いのため、パーサー・エンドポイントを
分ける必要がないと判断した。

### 実装構成

- `public/jra-entries-pdf.js`: クライアント側のPDF.js解析(NFKC正規化・ギャップ実測に
  よる行連結・発走時刻/開催情報検出・出走馬行解析・診断パネル)。既存の
  `public/jra-result-pdf.js`(レース結果PDFインポート)と同系統の手法を用いるが、
  実機未検証の結果PDFパーサーには手を入れず、**独立ファイル**として実装している
- `functions/api/races/entries-import.js`: 管理者専用API。マージ処理を行う
- `public/races.html`の「出走馬一覧PDFをインポート」ボタン(管理者のみ)からモーダルを開く

### マージロジック(レース行は絶対に削除・再作成しない)

`functions/api/races/results-import.js`と同じ「既存レースがあればUPDATE、なければ
INSERT」方式。レース行(`races.id`)を削除して作り直すことは絶対に行わない
(`prediction_marks`/`prediction_notes`が`ON DELETE CASCADE`で消えてしまうため)。

既存レースがある場合、`entries`を**馬名をキーに**1頭ずつマージする
(`functions/api/races/entries-import.js`の`mergeEntries()`):

- 新しい馬名 → `entries`に追加
- 既存の馬名で、取込側の`waku_number`/`horse_number`が**null** → 何もしない
  (未確定情報で既存の確定情報を誤って消さないため。木曜インポート後に金曜の
  データが来て初めて値が入る、という想定の流れを支える)
- 既存の馬名で、取込側が**値あり**、既存が**null** → 更新(木→金の確定フローは
  これで実現する)
- 既存の馬名に**既に確定済みの値があり、取込側が異なる値** → **自動上書きしない**。
  実運用ではまず発生しないイレギュラーな状態と想定し、インポート結果に
  「競合」として報告するのみに留める(管理者が手動で確認・対応する)
- 騎手名(`jockey`)は競合の概念を設けず、取込側の値があれば単純に上書きする
  (誤記修正等が入っても実害が小さいため)

`race_name`・`course_type`・`distance`は、既存が空の場合のみ埋める(既存の管理者入力を
上書きしない。`results-import.js`と同じ方針)。

### 予想情報の保護について

`prediction_marks`は`horse_number NOT NULL`かつ`UNIQUE(race_id, horse_number, user_id)`
のため、**馬番が確定するまでそもそも予想印は付けられない**(UI側でもセレクトを
disabledにしている)。一方`horse_notes`(馬メモ)は馬名がキーのため、馬番の有無に
関係なく最初から安全。

上記のマージ方式(race_id不変・確定済み値を無言で上書きしない)により、「金曜に
馬番確定→ユーザーが予想印を付ける→後で同じレースを再インポートしても予想が
消えない」という要件を満たす。「木曜(馬番なし)の時点で予想印を付ける」は
現行アーキテクチャ上不可能なため対象外。

### 実PDFでの検証結果(2026-08-08・確定後PDFで検証済み)

ユーザーから実際の「枠番・馬番確定後」PDF(`出走馬一覧_2026年8月8日_土曜_1回札幌5日.pdf`、
オッズ発表後の状態)を共有してもらい、以下が判明・修正済み:

- **枠番は確定後PDFでもテキストとして取得できない**(色付きアイコン表示のみ。JRAレース
  結果PDFと同じ制約)。行頭に「枠番→馬番」の2つの数字が並ぶという当初の推測は誤りで、
  実際は**馬番のみが単独の数字として現れる**。`waku_number`は今後も基本的に常にnullの
  ままとなる想定でよい(購入・予想印のガードは`horse_number`のみで判定しており影響なし。
  ただし**枠連馬券の払戻判定には影響するため、2026-08-09にその対策を実施した**。
  下記「払戻確定時のticket反映」参照)
- **オッズ発表後のPDFは行末に単勝オッズ(小数)が付く**。これを考慮せず「末尾2トークン=
  調教師名」としていたため、調教師名の一部が騎手名側に混入する不具合があった
  (`jraEntriesParseHorseRow()`で末尾の小数を事前に除去するよう修正)
- **ブリンカー(B)等のバッジが付く馬は、実PDFのテキスト抽出時に馬番だけが単独行になり、
  馬名以降が次の行に分離する**。「馬番だけの行」を検出したら次の行と結合してから
  解析するよう修正(`jraEntriesParseExtractedPages()`)
- **調教師名がスペース無しで1トークンに結合されるケースがある**(例: 「谷 潔」ではなく
  「谷潔」)。トークン数(2/3/4)と、外国人騎手名を示すピリオドの有無から騎手名・
  調教師名の境界を推定するロジックに変更した
- **マージ後にentriesを馬番順へソートし直す処理を追加**。以前は木曜(馬番なし・
  五十音順で登録)の並びが金曜の更新後もそのまま残ってしまい、レース管理画面の
  出走馬表モーダル(entries配列のi番目≒馬番(i+1)という前提で描画)で表示が崩れる
  不具合があった。枠番・馬番が未確定の間は引き続き馬名(五十音)順とする
- **`races.js`の`defaultWakuNumber()`(出走馬表モーダルでの枠番初期値の自動計算)が、
  過去に一度修正されていたはずの旧式ロジック(余りを若い枠番側に寄せる)に戻って
  しまっていたことが判明し、再修正した**(正: 余りは大きい枠番(7・8枠)側に寄せる)。
  この関数はPDFインポートとは独立した既存機能だが、インポート後の出走馬表モーダルで
  枠番が未確定(null)の馬に表示用の目安値を計算する際に使われるため、本フェーズの
  検証で不具合が可視化された

これらの修正により、実PDF(12レース・157頭)を通して解析エラー0件・馬番昇順・
騎手名/調教師名とも正しく取得できることを確認済み(Node上でのロジック検証。
実ブラウザのPDF.jsでの動作は引き続き未検証)。

### 実機(実ブラウザ)での検証結果(2026-08-09)

もう1件の実サンプル(中京、12レース・164頭)を実際にブラウザで解析・登録した結果、
**パーサー自体は診断ログ通り正確(解析失敗0件・実頭数と完全一致)だったにもかかわらず、
出走馬表モーダルを開くと馬名が空の行と実データの行が交互に並ぶ**という不具合が
報告された。

**原因**: パーサーの問題ではなく、`entries-import.js`のマージ処理側の不具合。
このレースのDB上の既存`entries`に、以前の何らかの操作(手動編集の保存ミスや、
過去のテストで生成された不完全なデータ等)で**馬名が空の行**が紛れ込んでいた。
マージは馬名をキーに突き合わせるため、馬名が空の既存行はどの馬とも一致せず、
削除も統合もされずに残り続け、新しくインポートされた実データが「別の新しい馬」
として追加され続けていた。その後の馬番順ソートで、同じ馬番を持つ「空行」と
「実データ行」が安定ソートにより隣り合って並んだ結果、交互に空欄が現れる見た目に
なっていた。

**修正**: `mergeEntries()`の冒頭で、既存entries側の**馬名が空の項目を除去**してから
マージするよう変更した(`functions/api/races/entries-import.js`)。新規レース作成
(INSERT)時にも念のため同様のフィルタを追加した。この修正により、次回以降の
インポートで自動的にクリーンアップされる(空行を持つレースへ再インポートすれば
解消する想定)。

### 特定の騎手のみ調教師名が連結してしまう不具合(2026-08-09・調査中)

**症状**: 上記の空行不具合修正後、実ブラウザでの再検証で「特定の騎手(松若風馬・
団野大成・松本大輝等、同一開催で複数レースに騎乗する乗り鞍の多い騎手)のみ、
騎手名に調教師名が連結してしまう」不具合が報告された。

**調査結果**: `pdftotext -layout`によるテキスト抽出では該当行も他の行と同様に
正常なスペース区切りで出力されており、テキストデータ自体・視覚的な確認では
他の騎手との違いが見当たらない。このため、**実ブラウザのPDF.jsが返す文字ごとの
座標・幅情報にのみ現れる差異**である可能性が高いと考えている(未確証)。

**推定原因(未確証)**: PDF内で同一文字列(騎手名リンク)が複数箇所で使われる場合、
PDF生成側が描画データを使い回す(キャッシュする)ことがあり、これによりPDF.jsが
報告する文字幅(prev.w)が実際の見た目と異なる値になっている可能性がある。
`jraEntriesJoinRowItems()`の区切り判定(連結/スペース/タブ)は`prev.w`に比例した
しきい値を使っているため、この値が異常だとしきい値が本来より大きくなり、
実際には区切りがある箇所を「連結」と誤判定してしまうと考えられる。

**現時点での対応**:
1. `jraEntriesNormalizeLine()`が行内のタブ(列区切りの情報)を早期にスペースへ
   一律変換していた根本的な設計不備を修正。タブは`jraEntriesJoinRowItems()`が
   実測ギャップから判定した信頼度の高い「列区切り」情報のため、
   `jraEntriesParseHorseRow()`まで保持し、タブがあれば最優先で騎手名/調教師名の
   境界として使うよう変更(以前はタブも即座にスペースへ変換されており、
   この情報が活用されていなかった)
2. 見習い減量記号(☆▲△★◇)を、以前は除去して捨てていたが、JRA表記に合わせて
   騎手名の先頭に保持するよう変更(ユーザー要望に対応)
3. ギャップしきい値の計算式に上限を設定(`JRA_E_GAP_SPACE_MAX`/`JRA_E_GAP_TAB_MAX`)。
   `prev.w`が異常値の場合でもしきい値が際限なく大きくならないようにする保険的対応
   (上記の推定原因が正しければ有効なはずだが、実測データでの確証はまだ無い)

**未解決**: 上記の推定が正しいかどうかは実機の「行内文字間隔サンプル」(診断パネル)の
実測値を確認しないと確証が持てない。次に同じ不具合が発生した場合は、該当行を含む
診断パネルのギャップサンプルを確認し、必要であれば`JRA_E_GAP_SPACE_RATIO`等の
しきい値自体を調整すること。なお、この不具合は騎手名の表示のみに影響し、
出走馬のマッチング(`horse_name`をキーにしたマージ)には影響しない。

### 今回のフェーズで対応していないこと(次フェーズ送り)

- **`trainer`(調教師名)**: PDFからは取得できるが、`entries`には保存しない
  (パーサー側で解析はするが送信直前に除外している)。次フェーズで`entries`に
  `trainer`フィールドを追加する際に改めて対応する(JSON拡張のためDBマイグレーション
  自体は不要だが、影響範囲確認のため段階を分けている)
- **枠番・馬番確定後PDFの実機検証**: 手元にある実サンプルはいずれも「枠番・馬番未確定」
  状態のもの。確定後PDFで行頭に「枠番→馬番」の順で数字が2つ並ぶという前提
  (`jraEntriesParseHorseRow()`)は、既存の一覧ページの列順(「枠 馬番 馬名 …」)からの
  推測であり、**実PDFでの検証はまだ行っていない**。実際に確定後PDFをインポートして
  ズレがあれば、パーサーのその部分を調整すること
- **競合の自動解決・上書きUI**: 競合が発生した場合、`alert()`のメッセージで一覧表示
  するのみ。管理画面上で個別に解決するUIは用意していない

## 認証・複数ユーザー対応(2026-08-01)

- 個別ログイン: ログイン画面の「新規ユーザー登録」から、誰でもユーザー名+パスワードで
  アカウントを自己登録できる(招待コード等の承認フローは無い)
- 管理者判定: DBにフラグを持たせず、Cloudflare Pagesの環境変数`ADMIN_USERNAMES`
  (カンマ区切りのユーザー名リスト)に含まれるユーザー名でログインした人だけを
  管理者として扱う。`functions/api/_shared.js`の`isAdminUsername()`で判定し、
  `functions/_middleware.js`がリクエストごとに`context.data.isAdmin`へセットする
- セッション: Cookieのペイロードに`user_id`・`username`・有効期限を含め、
  `env.APP_PASSWORD`をHMAC署名鍵として利用する(ログイン用パスワードとしては
  使わなくなったが、署名鍵としては流用している)
- データの所有者(user_id)を持つテーブル: `tickets`・`imported_tickets`・
  `imported_ticket_groups`・`prediction_notes`・`prediction_marks`・`horse_notes`。
  いずれも全APIハンドラで`WHERE user_id = ?`のフィルタ、新規作成時の`user_id`セットを
  行っており、他ユーザーのデータは常に「存在しない(404)」として扱う
  (`imported_ticket_items`自体はuser_idを持たず、`imported_ticket_groups`との
  JOIN経由で所有者を判定する)
- `races`(レース情報)は全ユーザー共有のデータであり、user_idを持たない。
  登録・編集・削除・開催日程の一括登録は管理者のみが行える
  (`functions/api/races/*`で`requireAdmin()`によりガードしている)。
  **`races`(共有)と`tickets`(ユーザーごとに分離)がまたがる処理を書く際は、
  「管理者が見えている・操作できているデータ」と「実際に更新すべき対象データ」が
  一致するとは限らない点に注意すること**(下記「払戻確定時のticket反映」の
  不具合・修正はこのズレが原因だった)
- CSVインポート時のレース自動作成は廃止した(2026-08-01)。レースが未登録のまま
  取り込まれたデータ(`imported_ticket_groups.race_id IS NULL`)は、管理画面
  (`admin.html`)の「未登録レース一覧」から確認でき、管理者がそのレースを登録すると
  `linkUnregisteredImportsToRace()`により自動的に紐付く
- 既存データ(個別ログイン導入前のデータ)の扱い: DBマイグレーション直後はuser_idが
  NULLのままなので、管理者アカウント作成後に`assign_existing_data_to_admin.sql`を
  1回実行して管理者アカウントへ一括で割り当てる運用とする(README参照)。
  「所有者を変更」する機能は用意していない(導入後は新規データが自動的に正しいユーザーへ
  紐づくため、変更する必要が無いと判断したため)

## データフロー

- 通常購入 → `tickets`
- Club JRA-Net等のCSV取込 → `imported_tickets`(原本)→ `imported_ticket_groups`(購入グループ)→ `imported_ticket_items`(個別買い目)
- 出走馬一覧PDF取込 → `races.entries`(馬名をキーにマージ。上記「出走馬一覧PDFインポート」参照)
- JRAレース結果PDF取込 → `races.entries`/`races.finish_order`/`races.payouts`(`results-import.js`)。**2026-08-09〜: 着順・払戻を更新した場合、このレースを購入した全ユーザーの`tickets.payout`も併せて再計算する(下記「払戻確定時のticket反映」参照)**
- 購入履歴画面では、通常購入とCSV取込履歴を統合して表示する(データの出所は保持したまま扱い、自動統合はしない)
- CSV APIレスポンス形式: `{ ok, items, imported, skipped }`

## CSV取込の仕様

- CSV 1行を購入グループとして保持し、組み合わせを個別買い目へ分解する
- 的中買い目は `is_hit=1`、払戻を該当買い目へ紐付ける
- **着順・払戻レートの反映(2026-07-31〜)**: CSV取込結果のうち、着順が一意に定まる情報は
  `races.finish_order` へ、的中組み合わせごとの払戻レート(100円あたり)は式別ごとに
  `races.payouts` へ反映する。
  - 着順: 単勝(1着のみ)・馬単(1・2着)・三連単(1〜3着)の的中が1行のみの場合に反映する。
    三連単からの情報を最も信頼できるものとして扱い、既に埋まっている着順スロットは
    (単勝・馬単からの)より情報量の少ないデータで上書きしない。三連複・馬連・ワイド等は
    どの馬が何着かという順序までは分からない(組み合わせの中の順不同)ため着順推測は行わない
  - 払戻レート: 全式別が対象。同じレース・式別・組み合わせに複数回の取込で異なるレートが
    来た場合は最新の値で上書きする
- CSVインポート時点では馬名・騎手が分からず、購入履歴(`imported_ticket_items.selections`)には
  馬番のみが入る。レース管理画面で出走馬表(馬名・騎手)を登録・更新すると、同じレース・馬番を
  参照している`imported_ticket_items`および`tickets`の`selections`へ馬名・騎手を書き戻す
  (バックフィルする、`functions/api/_shared.js`の`backfillHorseNamesForRace`)。
  既に値が入っている項目は上書きしない(新しい値が空の場合は何もしない)。**出走馬一覧PDF
  インポート(entries-import.js)も、`horse_number`が確定した(nullでなくなった)タイミングで
  同じ関数を呼び出しバックフィルを行う**
- 未登録レースは新規作成し、出走馬は空配列のままでもよい
- CSV原本は `imported_tickets` に残し続ける(正規化後も削除しない)
- 既存CSVデータも履歴APIで後方互換表示する
- 同一購入の自動統合は行わない
- 日付・受付番号がともに空の行(CSV末尾の「合計」行など)は購入データではないためスキップする
- Club JRA-Net購入履歴CSVは既に決着済みの購入履歴であり「未確定(結果待ち)」は存在しない。
  的中/返還列に値がある行は、的中買い目はrefundを、非的中買い目は0円をpayoutとして確定させる
  (的中/返還列が空の場合のみpayout=nullの未確定として扱う)
  - **要確認(2026-08-09時点)**: 出走取消等による「返還」(全額払戻)の行が「的中／返還」列に
    どのように表記されるかは、現物のサンプルCSVで未確認。もし「的中」という文字列を含まない
    形で返還が表現される場合、現状のロジックでは非的中(0円)として扱われてしまい、実際には
    購入額が全額返還される(収支への影響が±0になるはず)ケースを損失として計上してしまう
    可能性がある。返還が発生したCSVサンプルが手に入った時点で、`hit_refund`列の実際の
    表記を確認し、必要であれば`return_amount`列の値を`payout`計算に反映するよう修正すること
- 重複判定キー(`receipt_number`+`sequence_number`)には`race_date`も含める。受付番号は
  開催日ごとに採番がリセットされることがあるため、日付を含めないと別日の正当なデータが
  誤って重複扱いされ、CSV再取込時にスキップされてしまう不具合があった
- 「的中／返還」列に複数の的中組み合わせが含まれる行(BOX・ながし等で複数点的中した場合、
  例: `的中02―05／的中02―09／的中05―09`)は、組み合わせごとに分解して個別に払戻額を計算する。
  払戻額は「払戻単価」列(100円あたりのレート、こちらも同じ並び順で／連結される)を
  組み合わせごとの購入金額に乗じて算出する(`payout = round(rate / 100 * amount)`)。
  以前は行全体の払戻金額(合計)を1つの組み合わせにまとめて計上していたため、
  複数点的中の行で金額が合わなくなる不具合があった
- レース削除時は、そのレースに紐づく `imported_ticket_groups`／`imported_ticket_items` に加えて、
  参照元の `imported_tickets`(CSV原本)も削除する。CSV原本を消し忘れると、レースを削除しても
  購入履歴が「孤立データ」として残り続け、かつ同じCSVを再取込できなくなる不具合になる
- **実装上の注意(2026-08-01〜)**: `functions/api/ticket-imports/index.js`の`GET`/`POST`は、
  以前グループ・CSV行ごとに個別のD1クエリを発行するN+1実装になっており、取込件数が増えると
  Cloudflare Workersの1リクエストあたりのサブリクエスト数上限に抵触して500エラーになる
  不具合があった。現在は「一覧取得は関連テーブルを1回のクエリでまとめて取得しメモリ上で
  グループ化する」「CSV取込は既存重複チェック用のキーとレース参照をリクエスト単位で
  キャッシュし、重複候補検出は全行処理後に1回だけ行う」方式に変更し、クエリ回数を
  大幅に削減している。この関数(および同様に「1件ごとにDBへ問い合わせるループ」を含む
  実装)を今後変更・追加する際は、同じ問題を再発させないよう注意すること
- **集計への反映漏れ(2026-08-09時点・未確認)**: `GET /api/ticket-imports`が返す各アイテムには
  `race_finish_order`/`race_payouts`(通常購入`tickets`側にはJOINで付与されているレース確定
  情報)が含まれていない。そのため`stats.js`の的中率集計(`computeHitRate`)で、該当レースの
  先頭アイテムがCSVインポート分かつ`payout`が未確定(`null`)のままだった場合、実際には
  レース結果が確定していても「判定対象外」に漏れる可能性がある。CSVインポート分は
  取込時点で基本的に確定済みデータになる想定のため実害は限定的だが、根本対応としては
  `GET /api/ticket-imports`のレスポンスにも`race_finish_order`/`race_payouts`を含めることを
  検討する

- **`imported_ticket_groups`の一意制約について(2026-08-04確認・対応済み)**: `uq_imported_group_source_key`
  (`UNIQUE(source, group_key)`)には`user_id`を含めていない。これは意図的な設計であり、
  本アプリの複数ユーザー対応は「同じJRA-Netアカウントを複数のアプリユーザーが共有する」
  想定をしていないため、通常運用では異なるユーザー間で`group_key`(日付:受付番号:通番)が
  衝突することはない(スキーマ変更は不要と判断)。ただし、万が一(誤って他人のCSVを取り込んだ等)
  衝突した場合、以前はSQLiteのUNIQUE制約違反がそのままハンドリングされずリクエスト全体が
  500エラーで中断していた。現在は`imported_ticket_groups`へのINSERT箇所(`functions/api/ticket-imports/index.js`)
  でこの制約違反だけを検知し、該当行を「conflicted」として数えて`conflicts`配列(該当行の
  日付・競馬場・レース番号・式別・買い目と理由メッセージ)へ積み、他の行の取込処理は継続する
  ように変更した。レスポンスには`conflicted`件数・`conflicts`配列が追加され、購入履歴画面
  (`app.js`)のCSVインポート結果アラートに「◯件は別のユーザーが登録済みのデータと衝突した
  ため取り込めませんでした。」という案内が表示される。なお、衝突した行のCSV原本
  (`imported_tickets`)自体は(重複判定の対象外のため)保存されたままになる(「CSV原本は
  削除しない」という既存方針と一致)

### 「馬／組番」列の解析

CSV出力元によって表記ゆれがあるため、以下を吸収して解析する。

- 馬番の区切り文字: 半角/全角ハイフン、水平線(―)、各種ダッシュ、読点、矢印(→)など
- 購入方式ごとの表現:
  - 通常・複数点(セミコロン区切りで組み合わせを列挙): そのまま個別買い目として扱う
  - BOX(スラッシュなし・全馬番の羅列): 全馬番から式別の点数分のC(n,k)を生成
  - ながし・軸1頭/2頭(全角スラッシュ2群、軸＋相手群): 相手群から不足分を選び軸と組み合わせる
  - フォーメーション(全角スラッシュの群数が式別の点数と一致): 各群から1頭ずつ選ぶ直積
  - マルチ・馬単/三連単等の着順ありの式別: 生成した組み合わせの全順列を購入点数として扱う
- 購入金額列が「単価／合計」の複合表記(例: `200／3600`)の場合は合計(末尾の値)を採用する

## 日時表示のタイムゾーン(2026-08-10〜)

- D1の`created_at`等(`datetime('now')`で保存される列)はUTCの`"YYYY-MM-DD HH:MM:SS"`
  形式(タイムゾーン情報なし)で保存される。この文字列をそのまま`new Date()`に渡すと、
  末尾にタイムゾーン指定が無い形式の解釈がブラウザによって異なり(UTCとして解釈される
  とは限らない)、閲覧環境によって表示時刻がずれる可能性がある
- **管理画面(`admin.html`)の「登録ユーザー一覧」の登録日時**は、この問題を避けるため
  `public/admin.js`の`formatDateTime()`で明示的にUTCとしてパースしたうえで、
  `Intl.DateTimeFormat`の`timeZone: "Asia/Tokyo"`を使って常に日本時間(JST)に変換して
  表示する(閲覧者のブラウザのタイムゾーン設定に依存しない)。見出しにも「登録日時(JST)」
  と明記している
- 同様の「DBの生UTC文字列をブラウザのローカルタイムゾーン解釈に依存したまま表示している
  箇所」が他にも残っている可能性がある(例: 購入履歴カレンダーの「今日」判定等)。
  見つかった場合は同じ考え方(明示的にUTCとしてパース→`Asia/Tokyo`へ変換)で対応する

  高さを削ってページ間の高さのばらつきを抑える、という緩和策**(完全な解消を保証する
  ものではない)。`600px`以下では以下の通り変更した(`600px`超のPC画面は変更なし):

  - 前回(同じく2026-08-10)実施した「`.masthead-nav`折り返し修正」時に追加した

## 払戻確定時のticket反映(全ユーザー対応・2026-08-05)

**症状**: 管理者が払戻モーダルで着順・払戻レートを入力・保存しても、一般ユーザー
(管理者自身以外)の購入履歴・集計画面では該当馬券が「未確定」のまま表示され続ける
不具合があった。

**原因**: `races`(共有データ)と`tickets`(ユーザーごとに分離されたデータ)がまたがる
処理であるにもかかわらず、実装がユーザー分離を考慮していなかったこと。

- `races.js`の`loadTicketsForRace()`は`GET /api/tickets`(ログインユーザー自身の
  ticketsのみを返す)から取得した結果を`currentTickets`に保持していた
- 払戻保存時の`buildPayoutSubmission()`は、この`currentTickets`(=払戻モーダルを
  開いた管理者自身が購入したticketのみ)をもとに払戻金額を計算し、`PUT /api/tickets/:id`
  を個別に呼んで反映していた
- そのため、`races.finish_order`・`races.payouts`(共有テーブル)自体は全ユーザーに
  正しく反映されるが、**他ユーザーが購入した`tickets.payout`は一切更新されない**
  という状態になっていた

**修正内容**:

- 払戻計算ロジック(`public/payout.js`の`computeWinningCombos`・`ticketMatchesCombo`・
  `findStoredRate`相当)を`functions/api/_shared.js`にサーバー側実装として移植し、
  `recomputeTicketPayoutsForRace(db, raceId, finishOrder, payoutsObj, entries)`として
  公開した
- `functions/api/races/[id].js`の`onRequestPut`で、リクエストに`finish_order`または
  `payouts`が含まれていた場合、保存後に上記関数を呼び出し、**`user_id`で絞り込まず
  該当`race_id`の全`tickets`**を対象に払戻額を再計算・一括更新(`db.batch()`)する
  ように変更した
- `races.js`側の`buildPayoutSubmission()`・払戻フォーム送信処理からは、ticketを
  個別にPUTするループを削除した。`currentTickets`(`GET /api/tickets`由来)は、
  払戻モーダル内の「◯点購入」表示にのみ使用する(表示専用。反映処理には使わない)

**今後の注意点**: `races`(共有)と`tickets`/`prediction_marks`/`horse_notes`等
(ユーザーごとに分離)をまたぐ処理を新たに書く際は、「今操作しているユーザーから
見えているデータ」だけを更新対象にしないこと。全ユーザーに影響しうる変更
(着順・払戻の確定など)は、サーバー側で`user_id`条件を外して対象を洗い出す必要が
ないか、都度確認すること。出走馬一覧PDFインポート(`entries-import.js`)も同様の
考え方で、`race_id`をキーに全ユーザー分の`imported_ticket_groups`/`tickets`へ
`backfillHorseNamesForRace`を適用している(user_idで絞り込まない)。

### 追加修正1: JRAレース結果PDF一括登録でも再計算するように修正(2026-08-09)

**症状**: `functions/api/races/[id].js`(レース管理画面の払戻編集モーダルからの保存)には
上記の`recomputeTicketPayoutsForRace`が組み込まれていたが、**`functions/api/races/results-import.js`

**修正内容**: `results-import.js`で既存レースの`finish_order`/`payouts`を更新した場合に、
更新後の最新値を再取得したうえで`recomputeTicketPayoutsForRace`を呼び出すように変更した。
新規作成したレースについても、念のため(将来的な拡張で購入済みデータが紐付く可能性に備え)
着順・払戻が同時に入力されていれば呼び出すようにしている。

**今後の注意点**: `races.finish_order`/`races.payouts`を書き換えるコードパスを新規に
追加・変更する場合は、必ず`recomputeTicketPayoutsForRace`の呼び出しが漏れていないか
確認すること(2026-08-09時点の呼び出し元は`functions/api/races/[id].js`と
`functions/api/races/results-import.js`の2箇所)。

### 追加修正2: 枠番未確定時に「不的中(0円)」と誤判定しないように修正(2026-08-09)

**症状**: `races.entries`の`waku_number`が未確定(`null`)の出走馬が絡む枠連(wakuren)馬券は、
的中組み合わせ自体を算出できない(`computeWinningCombos`が`combo: null`を返す)。にもかかわらず
`computeTicketPayout`(クライアント側`public/payout.js`)・`recomputeTicketPayoutsForRace`
(サーバー側`functions/api/_shared.js`)のいずれも、的中組み合わせを算出できないケースを
最終的に「不的中(0円)」へフォールバックしていたため、実際には的中している可能性がある
枠連馬券まで一律に不的中(収支上の損失)として扱われてしまう不具合があった。特に
2026-08-07〜の出走馬一覧PDFインポート機能導入後は、確定後PDFでも枠番はテキスト抽出できず
`waku_number`が`null`のまま残るケースが標準的になりうるため、影響が顕在化しやすい状態だった。

**修正内容**: `computeWinningCombos`が返す組み合わせ配列に`combo: null`(判定不能)が
含まれる場合、`computeTicketPayout`/`recomputeTicketPayoutsForRace`のいずれも、
その馬券の払戻を「0円(不的中確定)」にせず`null`(未確定のまま)を返すように変更した。
枠連以外の式別(単勝・複勝・馬連・ワイド・馬単・三連複・三連単)は`wakuOf()`を使わないため
この変更による影響はない。

**留意点**: この修正はあくまで「以後の再計算で正しく判定不能として扱われるようになる」
というもので、修正前のロジックによって既に`payout=0`へ誤って確定されてしまっている
既存データを自動的に遡って直すものではない。該当レースの払戻を再保存する
(レース管理画面の払戻編集モーダルを開いて保存し直す、またはJRAレース結果PDFを
再インポートする)と、その時点で正しく`null`(未確定)へ補正される。枠番が未確定のまま
運用しているレースで枠連馬券が不自然に「不的中」表示になっている場合は、まず該当レースの
出走馬一覧PDFを枠番確定後のものへ再インポートし、`waku_number`を確定させることを優先する
(枠番が確定すれば判定不能ではなくなり、本来の的中判定が行われるようになる)。

## ロック仕様(2026-07-31 廃止)

通常購入(`tickets`)は、以前は着順・払戻の確定後に変更・削除をAPI側から拒否する
仕組み(ロック)を持っていたが、2026-07-31に**全面撤廃**した。本アプリは通常の
馬券購入アプリというより履歴管理が主目的(購入はおまけ)という位置づけのため、
確定後の編集・削除を禁止するほど厳格にする必要はないという判断による。

- `PUT /api/tickets/:id`・`DELETE /api/tickets/:id`とも、着順(`finish_order`)・
  払戻(`payouts`/`payout`)の確定有無にかかわらず常に許可する(409を返さない)
- フロント側(`app.js`の購入履歴画面)は元々ロック状態を意識したUI出し分けをしていない
  (編集用input・削除ボタンは常時表示)ため、フロント側の変更は不要だった
- レースの着順・払戻が確定した後の**新規購入**についても、2026-07-30に方針転換済み。
  一時期(同日)は「確定後は新規購入も禁止(409)」としていたが、購入履歴の登録し忘れに
  対応できないという問題があったため撤回し、**確定後も新規購入は引き続き可能**とした。
  予想画面の「このレースの馬券を購入」ボタンは、確定済みレースでは「結果確定済(購入する)」と
  表示が変わり、確定済みであることが分かるようにする(ボタン自体は無効化しない)。
  購入画面でも、確定済みレースを開くと案内バナーを表示するが、購入UI自体はブロックしない。
  **枠番・馬番が未確定の場合は例外で、購入UI自体をブロックする(上記「出走馬一覧PDF
  インポート」参照。実際の馬券は馬番が無いと購入できないため)**

## 集計ルール

- **収支・回収率**: 未確定(払戻未入力)の買い目も、購入した時点で金額を支払い済みとして
  分母(収支の減算対象・回収率の分母)に含める。実際の財布・口座残高のイメージであり、
  結果が出るまでは実質マイナス表示になるのは意図的な仕様(README「収支・回収率の考え方」参照)。
  ```
  収支   = 総払戻金額(確定分) − 総購入金額(未確定を含む全体)
  回収率 = 総払戻金額(確定分) ÷ 総購入金額(未確定を含む全体) × 100
  ```
- **的中率**: レース単位で、着順(`races.finish_order`)または払戻(`races.payouts`)の
  いずれかが確定していれば判定対象(分母)に含める。着順のみ確定していて払戻レートが
  未入力の場合、購入履歴側の`payout`はまだ設定されないため「不的中」側として扱われる
  (組み合わせと着順を照合した厳密な的中判定はしていない)。
  判定には `GET /api/tickets` が返す `race_finish_order` / `race_payouts`
  (レースをJOINして付与)を使用する。**`GET /api/ticket-imports`が返すCSVインポート分の
  アイテムにはこれらのフィールドが含まれていない点に注意(上記「CSV取込の仕様」の
  「集計への反映漏れ」参照)**

## CSSのキャッシュ対策(2026-08-02〜)

`style.css`は全画面(`admin.html`/`buy.html`/`index.html`/`prediction.html`/
`races.html`/`stats.html`)から`<link rel="stylesheet" href="style.css?v=YYYYMMDDHHmm">`
の形でバージョン付きクエリパラメータ付きで読み込む。Cloudflare Pagesや端末側の
キャッシュにより、デプロイ後もCSSの変更が反映されない事象があったため、
**CSSを変更してデプロイするたびに、このクエリパラメータの値(タイムスタンプ)を
全HTMLファイルで更新すること**。更新を忘れると、見た目の変更がユーザーに
反映されない場合がある。

## DBマイグレーションの運用(2026-08-03〜。node不要・wranglerコマンドのみで手動運用)

`latest1.sql`には**まだ本番へ適用していないスキーマ変更のみ**を、`-- @STEP: 名前`
ブロックとして末尾に追記していく。各ブロックが適用済みかどうかは、DB自身に
作成される`schema_migrations`テーブルに記録する(名前をキーに1行1件)。

適用手順(手動・wranglerのみ):

1. `latest1.sql`に新しい`-- @STEP: 名前`ブロックを追記する
2. そのブロックのSQLだけを一時ファイルにコピーし、まず`--local`で試してから
   `--remote`(本番)に適用する
3. 成功したら`schema_migrations`に`INSERT INTO schema_migrations (name) VALUES
   ('ステップ名');`で記録する
4. `latest1.sql`から該当ブロックを削除し、内容を`schema.sql`へ反映する(新規DBでも
   最初から最新構造になるように)。これにより`latest1.sql`は常に「これから適用す
   べき差分だけ」を保持する軽量な状態を保つ

DROP/RENAMEを伴う破壊的な変更は極力避け、`ALTER TABLE ADD COLUMN`や
`CREATE TABLE/INDEX IF NOT EXISTS`など、途中で失敗しても安全な内容にすること。
途中で失敗した場合は`PRAGMA table_info`等で実際にどこまで反映されているかを
確認してから、schema_migrationsへの記録や残りのSQLを個別に対応する。

以前はこの一連の判定・実行を`node scripts/migrate.js`に自動化させていたが、
Windows環境でNode.jsの子プロセス起動が不安定になる事象があったため、
2026-08-03にnode実行を廃止し、上記の手動手順に戻した。`scripts/migrate.js`は
`archive/scripts/`に履歴として残しているが、通常の運用では使用しない。

**破壊的変更を避けるルール**: 本番は既に運用中でユーザーの実データが
入っているため、`DROP TABLE`・`DELETE`・既存データを上書きする`UPDATE`など、
データやテーブルを削除・巻き戻す可能性のある変更は極力行わない。追加的な変更
(`ALTER TABLE ADD COLUMN`、`CREATE TABLE/INDEX IF NOT EXISTS`)を基本とし、
どうしても削除的な変更が必要な場合は、影響範囲を明示した上で作業前に必ず
ユーザーの承認を得ること。**なお、出走馬一覧PDFインポート機能(2026-08-07〜)の
`waku_number`/`horse_number`のnullable化は、`entries`がスキーマレスなJSON列である
ため、そもそもこのマイグレーション手順の対象外(DDL変更不要)である。**

## DBファイルの役割

- `schema.sql`: 新規DBを最新版で構築するための最終スキーマ。新規構築時に1回実行する
- `latest1.sql`: 既存DBを最新版へ更新するための統合マイグレーション。**未適用の
  `-- @STEP`ブロックのみ**を保持する(適用済みの内容は`schema.sql`に反映し、
  ファイルからは削除する)
- `archive/migrations/`: 過去の番号付きmigration(v2〜v10)・過去の`latest1.sql`の
  アーカイブ・単発マイグレーションファイルの履歴保管場所。通常のセットアップ・
  更新では使用しない
- `archive/scripts/migrate.js`: 以前使用していた自動適用ラッパー(廃止済み・履歴保管のみ)

新しいスキーマ変更を行う場合は、`schema.sql` と `latest1.sql` の両方を更新し、
このファイル(`docs/DESIGN.md`)の該当箇所も合わせて更新してください。
