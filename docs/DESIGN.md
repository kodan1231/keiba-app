# 設計方針

このドキュメントは現状の設計を常に表す「生きたドキュメント」です。
バージョン名(v9・v10等)では管理せず、変更があればこのファイル自体を上書き更新します。
個々の変更の経緯を残したい場合はコミットメッセージ側に記録してください。

## データ構造

| データ | テーブル | 備考 |
|---|---|---|
| 通常購入 | `tickets` | 購入グループ`group_id` + 組み合わせ1点=1行 |
| CSV原本(Club JRA-Net等) | `imported_tickets` | 外部CSVの原本をそのまま保持 |
| CSV購入グループ | `imported_ticket_groups` | CSVの1行=1購入グループ |
| CSV個別買い目 | `imported_ticket_items` | 組み合わせを個別買い目へ分解したもの |
| 予想印 | `prediction_marks` | **1頭につき1つまで**(2026-07-30〜。ドロップダウン選択式に変更。以前は複数登録可能だった)。印の種類: ◎○▲△☆消。2026-08-01よりユーザーごとに分離(`UNIQUE(race_id, horse_number, user_id)`) |
| 馬メモ | `horse_notes` | 馬名をキーに継続管理。馬名はtrim/空白正規化して保存。2026-08-01よりユーザーごとに分離(`UNIQUE(horse_name, user_id)`) |
| ユーザーアカウント | `users` | 2026-08-01追加。ログイン画面から自己登録できる(招待コード等の制限なし) |

## 認証・複数ユーザー対応(2026-08-01)

- 個別ログイン: ログイン画面の「新規ユーザー登録」から、誰でもユーザー名+パスワードで
  アカウントを自己登録できる(招待コード等の承認フローは無い)
- 管理者判定: DBにフラグを持たせず、Cloudflare Pagesの環境変数`ADMIN_USERNAMES`
  (カンマ区切りのユーザー名リスト)に含まれるユーザー名でログインした人だけを
  管理者として扱う。`functions/api/_shared.js`の`isAdminUsername()`で判定し、
  `functions/_middleware.js`がリクエストごとに`context.data.isAdmin`へセットする
- セッション: Cookieのペイロードに`user_id`・`username`・有効期限を含め、
  `env.APP_PASSWORD`をHMAC署名鍵として利用する(ログイン用パスワードとしては
  使わなくなったが、署名鍵としては流用している)
- データの所有者(user_id)を持つテーブル: `tickets`・`imported_tickets`・
  `imported_ticket_groups`・`prediction_notes`・`prediction_marks`・`horse_notes`。
  いずれも全APIハンドラで`WHERE user_id = ?`のフィルタ、新規作成時の`user_id`セットを
  行っており、他ユーザーのデータは常に「存在しない(404)」として扱う
  (`imported_ticket_items`自体はuser_idを持たず、`imported_ticket_groups`との
  JOIN経由で所有者を判定する)
- `races`(レース情報)は全ユーザー共有のデータであり、user_idを持たない。
  登録・編集・削除・開催日程の一括登録は管理者のみが行える
  (`functions/api/races/*`で`requireAdmin()`によりガードしている)
- CSVインポート時のレース自動作成は廃止した(2026-08-01)。レースが未登録のまま
  取り込まれたデータ(`imported_ticket_groups.race_id IS NULL`)は、管理画面
  (`admin.html`)の「未登録レース一覧」から確認でき、管理者がそのレースを登録すると
  `linkUnregisteredImportsToRace()`により自動的に紐付く
- 既存データ(個別ログイン導入前のデータ)の扱い: DBマイグレーション直後はuser_idが
  NULLのままなので、管理者アカウント作成後に`assign_existing_data_to_admin.sql`を
  1回実行して管理者アカウントへ一括で割り当てる運用とする(README参照)。
  「所有者を変更」する機能は用意していない(導入後は新規データが自動的に正しいユーザーへ
  紐づくため、変更する必要が無いと判断したため)

## データフロー

- 通常購入 → `tickets`
- Club JRA-Net等のCSV取込 → `imported_tickets`(原本)→ `imported_ticket_groups`(購入グループ)→ `imported_ticket_items`(個別買い目)
- 購入履歴画面では、通常購入とCSV取込履歴を統合して表示する(データの出所は保持したまま扱い、自動統合はしない)
- CSV APIレスポンス形式: `{ ok, items, imported, skipped }`

## CSV取込の仕様

- CSV 1行を購入グループとして保持し、組み合わせを個別買い目へ分解する
- 的中買い目は `is_hit=1`、払戻を該当買い目へ紐付ける
- **着順・払戻レートの反映(2026-07-31〜)**: CSV取込結果のうち、着順が一意に定まる情報は
  `races.finish_order` へ、的中組み合わせごとの払戻レート(100円あたり)は式別ごとに
  `races.payouts` へ反映する。
  - 着順: 単勝(1着のみ)・馬単(1・2着)・三連単(1〜3着)の的中が1行のみの場合に反映する。
    三連単からの情報を最も信頼できるものとして扱い、既に埋まっている着順スロットは
    (単勝・馬単からの)より情報量の少ないデータで上書きしない。三連複・馬連・ワイド等は
    どの馬が何着かという順序までは分からない(組み合わせの中の順不同)ため着順推測は行わない
  - 払戻レート: 全式別が対象。同じレース・式別・組み合わせに複数回の取込で異なるレートが
    来た場合は最新の値で上書きする
- CSVインポート時点では馬名・騎手が分からず、購入履歴(`imported_ticket_items.selections`)には
  馬番のみが入る。レース管理画面で出走馬表(馬名・騎手)を登録・更新すると、同じレース・馬番を
  参照している`imported_ticket_items`および`tickets`の`selections`へ馬名・騎手を書き戻す
  (バックフィルする、`functions/api/_shared.js`の`backfillHorseNamesForRace`)。
  既に値が入っている項目は上書きしない(新しい値が空の場合は何もしない)
- 未登録レースは新規作成し、出走馬は空配列のままでもよい
- CSV原本は `imported_tickets` に残し続ける(正規化後も削除しない)
- 既存CSVデータも履歴APIで後方互換表示する
- 同一購入の自動統合は行わない
- 日付・受付番号がともに空の行(CSV末尾の「合計」行など)は購入データではないためスキップする
- Club JRA-Net購入履歴CSVは既に決着済みの購入履歴であり「未確定(結果待ち)」は存在しない。
  的中/返還列に値がある行は、的中買い目はrefundを、非的中買い目は0円をpayoutとして確定させる
  (的中/返還列が空の場合のみpayout=nullの未確定として扱う)
- 重複判定キー(`receipt_number`+`sequence_number`)には`race_date`も含める。受付番号は
  開催日ごとに採番がリセットされることがあるため、日付を含めないと別日の正当なデータが
  誤って重複扱いされ、CSV再取込時にスキップされてしまう不具合があった
- 「的中／返還」列に複数の的中組み合わせが含まれる行(BOX・ながし等で複数点的中した場合、
  例: `的中02―05／的中02―09／的中05―09`)は、組み合わせごとに分解して個別に払戻額を計算する。
  払戻額は「払戻単価」列(100円あたりのレート、こちらも同じ並び順で／連結される)を
  組み合わせごとの購入金額に乗じて算出する(`payout = round(rate / 100 * amount)`)。
  以前は行全体の払戻金額(合計)を1つの組み合わせにまとめて計上していたため、
  複数点的中の行で金額が合わなくなる不具合があった
- レース削除時は、そのレースに紐づく `imported_ticket_groups`／`imported_ticket_items` に加えて、
  参照元の `imported_tickets`(CSV原本)も削除する。CSV原本を消し忘れると、レースを削除しても
  購入履歴が「孤立データ」として残り続け、かつ同じCSVを再取込できなくなる不具合になる
- **実装上の注意(2026-08-01〜)**: `functions/api/ticket-imports/index.js`の`GET`/`POST`は、
  以前グループ・CSV行ごとに個別のD1クエリを発行するN+1実装になっており、取込件数が増えると
  Cloudflare Workersの1リクエストあたりのサブリクエスト数上限に抵触して500エラーになる
  不具合があった。現在は「一覧取得は関連テーブルを1回のクエリでまとめて取得しメモリ上で
  グループ化する」「CSV取込は既存重複チェック用のキーとレース参照をリクエスト単位で
  キャッシュし、重複候補検出は全行処理後に1回だけ行う」方式に変更し、クエリ回数を
  大幅に削減している。この関数(および同様に「1件ごとにDBへ問い合わせるループ」を含む
  実装)を今後変更・追加する際は、同じ問題を再発させないよう注意すること

### 「馬／組番」列の解析

CSV出力元によって表記ゆれがあるため、以下を吸収して解析する。

- 馬番の区切り文字: 半角/全角ハイフン、水平線(―)、各種ダッシュ、読点、矢印(→)など
- 購入方式ごとの表現:
  - 通常・複数点(セミコロン区切りで組み合わせを列挙): そのまま個別買い目として扱う
  - BOX(スラッシュなし・全馬番の羅列): 全馬番から式別の点数分のC(n,k)を生成
  - ながし・軸1頭/2頭(全角スラッシュ2群、軸＋相手群): 相手群から不足分を選び軸と組み合わせる
  - フォーメーション(全角スラッシュの群数が式別の点数と一致): 各群から1頭ずつ選ぶ直積
  - マルチ・馬単/三連単等の着順ありの式別: 生成した組み合わせの全順列を購入点数として扱う
- 購入金額列が「単価／合計」の複合表記(例: `200／3600`)の場合は合計(末尾の値)を採用する

## 画面仕様

- **購入履歴画面(`index.html`)**: 常にカレンダーを表示し、日付を選択して初めてその日の
  購入履歴(詳細)が表示される(2026-07-30〜。以前は「日付から選ぶ」ボタンでカレンダーの
  表示/非表示を切り替える方式で、初期状態では全期間の履歴が一覧表示されていた)。
  サマリー(総購入・総払戻・収支・回収率)は選択日にかかわらず常に全期間を集計する
- **レース管理画面(`races.html`)**: 購入履歴画面と同様のカレンダーを追加し、
  登録済みレースがある日をカレンダー上でマーク、日付をクリックするとその日のレースだけに
  絞り込める(2026-07-30〜。以前は登録済みの全日付を上から下へスクロールして探す必要があった)
- **集計画面(`stats.html`)**: レース別・競馬場別・騎手別の3表とも、列見出し(購入/払戻/収支/
  回収率/的中率、および先頭列)をクリックすると、その列で昇順⇔降順を切り替えられる
  (2026-07-30〜)。初期表示のソート順は以下の通り:
  - レース別: 日付・競馬場・レース番号の順(3つを連結したキーで比較。日付が新しい順)
  - 競馬場別・騎手別: 購入金額の多い順(従来通り)
  数値列(購入/払戻/収支/回収率/的中率)は初回クリックで降順、文字列・日付列(先頭列)は
  初回クリックで昇順から始まる。値がnull(未確定で回収率・的中率が算出できない行)は
  ソート方向によらず常に末尾に表示する
- **購入画面(`buy.html`)の三連複・三連単「2頭軸」**: 1つの馬番リストの中で、各馬の行に
  「軸」(最大2頭まで選択)・「相手」のチェックボックスを並べる形式(JRA/netkeiba風、
  2026-07-31〜)。ある馬を軸として選ぶとその馬は相手として選べなくなり(逆も同様)、
  軸を既に2頭選んでいる状態では他の馬の「軸」チェックは無効化される。
  以前は「軸馬①」「軸馬②」「相手」の3つの縦リスト(それぞれ全頭分)が並ぶ構成で、
  出走頭数が多いと非常に縦長になる問題があった
- **予想登録画面(`prediction.html`)のレイアウト(2026-07-31〜)**:
  - ヘッダーの表示順は「日付・競馬場名・レース番号・レース名・頭数」。
    競馬場名・レース番号は(ページ遷移を伴わない)セレクトになっており、
    同じ開催日の他の競馬場・レースへその場で切り替えられる
    (以前はカレンダー画面へ戻る手段がなく、別レースを見るには`buy.html`の
    カレンダーから選び直す必要があった)
  - 「このレースの馬券を購入」ボタンはヘッダー内(レース名の近く)に配置し、
    出走頭数が多いレースでも下までスクロールせずに購入画面へ進めるようにした
  - 馬一覧を上部、購入済み馬券の一覧を下部に配置する順序に変更した
    (以前は購入済み馬券一覧が馬一覧より上にあった)

## レスポンシブ対応(2026-08-02〜)

- ブレークポイントは2段階: `700px`以下(タブレット〜大きめスマホ、既存)、
  `430px`以下(iPhone SE3等の小型スマホ、新規追加)。`430px`以下のルールは
  `700px`以下のルールに追加で重ねる形で適用され、`700px`超(PC)のレイアウトは
  変更しない
- **購入画面(`buy.html`)の組み合わせ選択表**(`.bet-horse-row`。単勝〜三連単・
  2頭軸まで共通の馬選択UI): `430px`以下では、馬名を折り返さず1行に収め、
  はみ出した分は省略(`…`)表示にする。チェックボックス/ラジオ欄は横並びを
  維持したまま**固定幅**で確保し(`auto`にすると内容量に応じて幅を奪い合い、
  馬名側が極端に狭くなる不具合があったため、固定幅とした)、枠番・馬番の
  列幅もさらに縮小する。列配分は「枠番・馬番は最小限、馬名を最優先、印欄は
  縮小、チェック欄は3個分の固定幅を確保」という優先順位
  - **既知の不具合と修正(2026-08-02)**: 印(`.bet-horse-mark`)列に旧ルール
    (2026-07頃実装、`grid-column:4;grid-row:1`)の`grid-row:1`が残っており、
    CSS Gridの自動配置仕様上「行が固定・列が自動」の要素は他の要素より
    先に配置されるため、印列が列1に割り込み、以降の枠番・馬番・馬名・
    チェック欄が1列ずつ右にズレる不具合があった(結果、馬名列に馬番が
    入り、印列(最も狭い18px)に馬名が入ってしまっていた)。
    `.bet-horse-mark`に`grid-row:auto`を明示することで解消済み。
    今後この行のCSSを触る際は、`grid-column`だけでなく`grid-row`も
    リセットされているか確認すること
- **購入履歴画面(`index.html`)のCSVインポートボタン**: `700px`以下では
  `#csv-import-btn`(と隠しファイル入力)を非表示にする。CSVインポート機能・
  APIは変更せず残し、表示のみを制御する(PCからの利用のみを想定)

## レース登録・編集

- レース新規登録(`POST /api/races`)・編集(`PUT /api/races/:id`)のどちらでも、
  出走馬表(`entries`)と同時に着順(`finish_order`)・払戻(`payouts`)を保存できる。
  以前は新規登録時のみ`entries`しか保存されず、同時に入力した着順が消えてしまう不具合があった
- `finish_order`は「1〜3着の馬番」のみを保存する(2026-07-30〜)。払戻計算(`computeWinningCombos`)は
  的中判定に上位3着までしか使わないため、4着以降の情報は不要。以前は出走馬表の各行に「着」の
  セレクトを設け、出走馬名の登録と密結合の形で全頭分の着順を入力させていたが、
  出走頭数が多いと入力・スクロールの手間が大きい上、払戻金額の入力そのものが
  出走馬表(馬名)の登録に依存してしまっていた。現在は出走馬表とは独立した
  「1着/2着/3着」の3つのセレクト(馬番のみ)で着順を入力する方式に変更し、
  馬名や出走馬表が未登録でも、馬番さえ分かれば払戻金額を入力できるようにした
- 払戻入力欄(馬券式別)は常に表示され、該当式別の判定に必要な着順(例: 単勝は1着のみ、
  三連単は3着まで)が入力されていない間は「◯着まで入力すると表示されます」という
  案内のみを表示する。着順を入力すると、その式別の的中組み合わせ入力欄が現れる

## ロック仕様(2026-07-31 廃止)

通常購入(`tickets`)は、以前は着順・払戻の確定後に変更・削除をAPI側から拒否する
仕組み(ロック)を持っていたが、2026-07-31に**全面撤廃**した。本アプリは通常の
馬券購入アプリというより履歴管理が主目的(購入はおまけ)という位置づけのため、
確定後の編集・削除を禁止するほど厳格にする必要はないという判断による。

- `PUT /api/tickets/:id`・`DELETE /api/tickets/:id`とも、着順(`finish_order`)・
  払戻(`payouts`/`payout`)の確定有無にかかわらず常に許可する(409を返さない)
- フロント側(`app.js`の購入履歴画面)は元々ロック状態を意識したUI出し分けをしていない
  (編集用input・削除ボタンは常時表示)ため、フロント側の変更は不要だった
- レースの着順・払戻が確定した後の**新規購入**についても、2026-07-30に方針転換済み。
  一時期(同日)は「確定後は新規購入も禁止(409)」としていたが、購入履歴の登録し忘れに
  対応できないという問題があったため撤回し、**確定後も新規購入は引き続き可能**とした。
  予想画面の「このレースの馬券を購入」ボタンは、確定済みレースでは「結果確定済(購入する)」と
  表示が変わり、確定済みであることが分かるようにする(ボタン自体は無効化しない)。
  購入画面でも、確定済みレースを開くと案内バナーを表示するが、購入UI自体はブロックしない。

## 集計ルール

- **収支・回収率**: 未確定(払戻未入力)の買い目も、購入した時点で金額を支払い済みとして
  分母(収支の減算対象・回収率の分母)に含める。実際の財布・口座残高のイメージであり、
  結果が出るまでは実質マイナス表示になるのは意図的な仕様(README「収支・回収率の考え方」参照)。
  ```
  収支   = 総払戻金額(確定分) − 総購入金額(未確定を含む全体)
  回収率 = 総払戻金額(確定分) ÷ 総購入金額(未確定を含む全体) × 100
  ```
- **的中率**: レース単位で、着順(`races.finish_order`)または払戻(`races.payouts`)の
  いずれかが確定していれば判定対象(分母)に含める。着順のみ確定していて払戻レートが
  未入力の場合、購入履歴側の`payout`はまだ設定されないため「不的中」側として扱われる
  (組み合わせと着順を照合した厳密な的中判定はしていない)。
  判定には `GET /api/tickets` が返す `race_finish_order` / `race_payouts`
  (レースをJOINして付与)を使用する。

## CSSのキャッシュ対策(2026-08-02〜)

`style.css`は全画面(`admin.html`/`buy.html`/`index.html`/`prediction.html`/
`races.html`/`stats.html`)から`<link rel="stylesheet" href="style.css?v=YYYYMMDDHHmm">`
の形でバージョン付きクエリパラメータ付きで読み込む。Cloudflare Pagesや端末側の
キャッシュにより、デプロイ後もCSSの変更が反映されない事象があったため、
**CSSを変更してデプロイするたびに、このクエリパラメータの値(タイムスタンプ)を
全HTMLファイルで更新すること**。更新を忘れると、見た目の変更がユーザーに
反映されない場合がある。

## DBファイルの役割

- `schema.sql`: 新規DBを最新版で構築するための最終スキーマ。新規構築時に1回実行する
- `latest1.sql`: 既存DBを最新版へ更新するための統合マイグレーション。既存DB更新時に1回実行する
- `archive/migrations/`: 過去の番号付きmigration(v2〜v10)の履歴保管場所。通常のセットアップ・更新では使用しない

新しいスキーマ変更を行う場合は、`schema.sql` と `latest1.sql` の両方を更新し、
このファイル(`docs/DESIGN.md`)の該当箇所も合わせて更新してください。
