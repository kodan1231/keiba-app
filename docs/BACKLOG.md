## クラスタO: 返還(refund)処理(2026-08-19設計・2026-08-20実装完了)

**背景**: JRAでは、出走取消・競走除外となった馬が絡む組み合わせ馬券(その馬を含む馬連・
馬単・ワイド・枠連・三連複・三連単等)は、「不的中」ではなく「返還」扱いとなり、購入金額が
全額払い戻される。**「競走中止」(発走後にレース中に競走を中止した馬)は返還の対象外**
(発走している=競走に参加しているため、通常通り不的中判定される)。以前は返還の概念自体が
無く、該当する馬券が「不的中(0円)」として誤って扱われていた。

**確定した仕様・実装内容**:
- `tickets`テーブルに`refunded INTEGER NOT NULL DEFAULT 0`カラムを追加(非破壊的変更)。
  `payout`(返還時は購入金額と同額)とは別に、「返還によるものか的中によるものか」を
  区別するフラグとして持たせる
- 判定は`races.payouts.refunds`(`jraResultParseRefund()`が既に抽出・保存していた
  返還馬番・返還同枠の情報)を使う。馬番ベースの式別(単勝・複勝・馬連・馬単・ワイド・
  三連複・三連単)は買い目の馬番いずれかが返還馬番に含まれれば返還、枠連は買い目の枠番
  いずれかが返還同枠に含まれれば返還と判定する
- 「中止」は`refunds`配列に一切追加されないため、追加のステータス判定ロジックを
  実装せずとも自然に返還対象から除外される
- サーバー側(`functions/api/_shared.js`)・クライアント側(`public/payout.js`)の両方に
  同じ判定ロジックを実装(既存方針の踏襲)
- `stats.js`の的中率集計は`payout > 0 && !refunded`に変更し、返還を的中としてカウント
  しないようにした。収支・回収率計算は変更不要(返還は収支±0になるよう設計されているため)
- 購入履歴・予想登録画面の買い目明細行で、返還時は「払戻¥X」ではなく「返還¥X」と表示する

詳細な仕様は`docs/DESIGN.md`「返還(refund)処理」節を参照。

**対象範囲**: JRAレース結果PDFインポート由来の通常購入(`tickets`)のみ。CSVインポート
由来(`imported_tickets`/`imported_ticket_items`)は対象外のまま(下記クラスタEに残置)。

実行環境を用いない静的コードレビューにより発見。3件ともユーザーとの確認により修正方針を
確定済み(N-2は実装完了・アーカイブ参照、N-4は
2026-08-16追加。)。

#### N-1(中優先度): 出走馬表(races.js)で馬番が重複入力できてしまう

**症状**: `public/races.js`の出走馬表フォーム(`entry-form-row`)は、各行の馬番セレクトが
互いに独立しており、同じ馬番を複数行に設定できてしまう。馬番が重複すると、購入時の
組み合わせ紐付けや`computeWinningCombos`による的中判定が意図しない挙動になる可能性がある。

**発生源の切り分け(確認済み)**:
- 手入力(レース管理画面): 対応要
- PDFインポート系(`jra-entries-pdf.js`/`jra-result-pdf.js`経由): **対応不要**。
  重複が起きるとすればパーサー側の解析バグであり、今回のスコープには含めない
  (再現・報告があれば別タスクとして起票する)

**確定した修正方針(クライアント側のみ・スワップ方式)**:

`public/races.js`の出走馬表フォームで、ある行の馬番セレクト(`.e-horse-number`)の値を
変更した際、**送信前の時点で**重複が起きないよう、UIの操作性で防ぐ。

- 各行の馬番セレクトに、現在選択されている値を`dataset.horseNumber`として保持しておく
  (`renderEntryRows()`描画時に初期値をセットし、以後の変更のたびに更新する)
- ある行(行X)の馬番セレクトが新しい値`V`に変更されたとき:
  1. 他の行(行Y)の中で、現在の馬番が`V`である行を探す
  2. 見つかった場合、行Yの馬番セレクトの値を「行Xの変更前の値」に**入れ替える**
     (単純なブロック/警告ではなく、2行の値をスワップすることで「常に1〜出走頭数の
     数値が重複なく1つずつ使われている」状態を維持する。ユーザーが「1」を選んだ行を
     後から別の行でも「1」に変えた場合、元々「1」だった行は自動的に元の行が持っていた
     番号に変わる、という挙動になる)
  3. スワップ後、両方の行の`dataset.horseNumber`を更新する
- 出走頭数変更時(`horseCountSelect`のchangeイベント)の再描画(`renderEntryRows`)でも、
  同様に初期値の`dataset.horseNumber`をセットし直す

**対象外とする範囲(確認済み)**:
- 枠番(`waku_number`)は9頭以上のレースで複数馬が同じ枠を共有するのが正常な状態のため、
  重複チェック・スワップ処理の対象**外**
- サーバー側(`functions/api/races/index.js`・`[id].js`)への重複チェック追加は、
  クライアント側のスワップ方式で通常操作では重複が発生しなくなるため、**今回は追加しない**
  (API直叩き等の迂回経路への防御は、必要になった時点で別途検討する低優先度項目として
  下記「今後の検討候補」に残す)
- PDFインポート経由(`entries-import.js`のマージ結果)での重複チェックは対象外
  (上記の通り、発生すれば解析バグとして別途扱う)

**実装対象ファイル**: `public/races.js`(`renderEntryRows()`・馬番セレクトの`change`
イベントハンドラ)のみ。

#### N-3(低優先度・記録のみ): ログアウトAPIが未認証(セッション切れ)状態だと401になりCookieが消えない

**症状**: `functions/_middleware.js`の`isPublicAuthRoute`判定は`/api/auth/login`・
`/api/auth/register`のみを未認証アクセス許可の対象にしており、`/api/auth/logout`は
含まれていない。セッションCookieが既に無効(期限切れ・破損・削除済み)な状態で「退場」
ボタンを押すと、`POST /api/auth/logout`自体が(ミドルウェアにより)401で弾かれ、
Cookieクリア処理(`Set-Cookie`によるMax-Age=0)まで到達しない。

**影響度(確認済み・低)**: `authedFetch`が401を検知した時点で`login-screen`を表示する
実装になっているため、体感としては「ログアウトできている」ように見え、実害はほぼない。
古いCookieが残ったままになるだけで、次回の正常ログイン時には新しいセッションCookieで
上書きされるため実質的な問題は生じない。

**確定した対応方針**: **今回は実装せず、方針の記録のみに留める**(ユーザー確認済み)。
将来対応する場合は以下の方針で対応する。

```js
// functions/_middleware.js
const isPublicAuthRoute =
  url.pathname === "/api/auth/login" ||
  url.pathname === "/api/auth/register" ||
  url.pathname === "/api/auth/logout";
```

`logout.js`はセッション内容を一切参照せず、常にCookieクリアのレスポンスを返すだけの
処理のため、認証チェックを外しても情報漏洩・不正操作のリスクはない(誰が呼んでも
「Cookieを消す」以上のことはできない)。

## 出走情報・払戻情報の自動取得について(調査結果)

「レース登録画面/払戻入力画面に取得ボタンを置き、開いているレース1件分だけをその場で
取得する」というUI案が出たが、1件ずつであっても呼び出せるHTTP経由の取得口がそもそも
存在しないため、保留とする。

- **JRA-VAN Data Lab.**(公式・月額サブスクリプション): 唯一のインターフェースが
  「JV-Link」というWindows専用のActiveX COMコンポーネント。Cloudflare Pages Functions
  (サーバーレスのJavaScript実行環境)からは技術的に呼び出せない
- **JRA公式サイト(jra.go.jp)への直接アクセス**: bot対策により即座にブロックされることを
  確認済み。利用規約の文言以前に、技術的にアクセスできない
- **netkeiba**: 利用規約でスクレイピングを明示的に禁止している

選択肢(いずれも保留中。方針転換する場合は下記から選ぶ):

- A. 貼り付け方式・PDFアップロード方式を磨く方向で進める(現状の方針。出走馬一覧PDF
  インポート・JRAレース結果PDFインポートもこの延長で対応している)
- B. 有料のスクレイピング代行API(Bright Data等)を利用する。技術的には可能だが月額コストが
  発生し、対象サイトの規約違反リスクが完全になくなるわけではない
- C. Windows常時稼働機を別途用意し、JV-Linkを使った中継サーバーを立てる(JRA-VAN公式のため
  規約面は最もクリーンだが、インフラ運用の手間が大きい)

## 馬券かご 確定仕様

目的: 複数レース・複数式別にまたがる買い目を、都度保存せずに一時的にためておき、
最後にまとめて保存する。netkeiba・楽天競馬の「馬券かご」相当。

確定した仕様:

- 対象範囲は「レースをまたいでよい」。複数レース・複数式別の買い目を1つのかごに貯められる
- 現行の「式別を選んで組み合わせ選択→即保存」という都度保存の購入フローは廃止し、
  「かごに追加」→(必要なだけ繰り返す)→「まとめて購入する」の流れに一本化する
  (1点だけ買いたい場合も、必ずかごを経由する)
- かごの中身はブラウザ/端末を閉じたり、後日開き直しても保持されている必要がある。
  → サーバー保存(下書きテーブル)までは不要と判断し、localStorageに保存する方式とする
    (同一端末・同一ブラウザ内でのみ保持され、他の端末とは同期されない想定。複数端末での
    同期が必要になった場合は、サーバー側に下書き用テーブルを追加する改修が別途必要になる)
- 「まとめて購入する」実行時は、かご内の全買い目を1回のAPIリクエストで送信し、サーバー側は
  `db.batch()`でまとめて書き込む(行ごとに個別リクエストをループする実装にはしない。
  過去にCSVインポートでN+1クエリによるサブリクエスト数上限超過が起きた教訓を踏まえる)

画面イメージ:

- 購入画面(buy.html)に「かご」パネルを常設(右側 or 下部)。ヘッダー等にも
  「かご: n点 / 合計¥xxx」のように現在の内容を常時表示する
- かご内の各行: 日付・競馬場・レース番号・式別・買い目内容・金額・削除ボタン
- かご下部: 合計点数・合計金額、「まとめて購入する」ボタン、「かごを空にする」ボタン
- 保存成功後はかごを空にし(localStorageもクリア)、購入履歴に反映する

実装時の主な変更点(見積り):

- buy.js: 「購入する」ボタンを「かごに追加」ボタンに置き換え、かご状態(localStorage)の
  読み書き・かごパネルの描画・合計計算を追加。レース遷移時もかごの内容を保持する
- functions/api/tickets/bulk.js(または同等の一括保存API): 複数レース・複数式別が混在した
  買い目配列を受け取れるよう、リクエスト形式を拡張(現状は1レース分の想定になっていないか要確認)
- localStorageのキーはログインユーザーごとに分ける(同じ端末を家族で共用した際にかごが
  混ざらないようにする)配慮が必要
