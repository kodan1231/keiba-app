### クラスタ12: 出走馬一覧PDFインポート(馬番なし/あり統合)【2026-08-07 設計承認済み・未実装】

ユーザーの1週間の運用フロー(月火水: 開催日程を手動登録／木: 出走馬一覧(馬番なし)を
インポート／金: 出走馬一覧(馬番あり)をインポート／土日: 払戻一覧をインポート)のうち、
「木・金の出走馬一覧インポート」に対応する新機能。月火水(開催日程)・土日(払戻)は
既存の「開催日程を一括登録」「JRAレース結果PDFをインポート」がそのまま使える。

**サンプルPDFの実物確認結果**(`出走馬一覧2026年8月8日_土曜_1回札幌5日.pdf`・
`出走馬一覧2026年8月9日_日曜_2回中京6日.pdf`で確認済み):
- JRA公式サイトの「出走馬一覧」ページのPDF保存。1開催日につき12レース分・1ファイル
- 各レースブロックのヘッダー: `発走時刻：10時00分` → レース名(例:「3歳未勝利」
  「第62回 CBC賞」等の特別戦名) → 条件・コース(例:「1,700メートル（ダート・右）」。
  障害戦は方向表記なし: 「3,000メートル（芝）」)
- 出走馬表は **馬名・性齢・負担重量・騎手名・調教師名のみ**。**枠番・馬番・馬体重列は
  空欄(未定)** ← これが「馬番なし」出走馬一覧の実体
- 騎手名には見習い減量記号(☆▲△★◇)や、姓名2語の日本語表記に当てはまらない外国人
  騎手名(例: `J.コレット`)が混在する
- レース番号(1R,2R…)はテキスト中に明記されない。既存の`results-import.js`と同様、
  「同一開催日・競馬場内での出現順」で1R,2R…と推測する方式で対応する

#### 承認済みの設計方針

**① 木・金は1つの機能に統合する**
出走馬一覧PDFは「馬番あり/なし」でフォーマットが同一(枠番・馬番列が埋まっているかどうか
だけの違い)。そのため新規インポート機能を1つ作り、枠番・馬番はPDFにあれば読み取り、
なければnullのまま登録する。木曜(馬番なし)にインポート→金曜(馬番あり)に**同じ機能で
再インポート**すれば、既存データが自動的に更新される設計とする。

**② DBスキーマ変更は無し。`races.entries`のJSON構造を拡張するのみ**
`entries`は元々スキーマレスなJSON配列(`entries TEXT NOT NULL`)のため、テーブル定義
変更は不要。
- `horse_number` / `waku_number` を **nullable** として扱う(PDFに値がなければnull)
- 馬の同一性は `horse_number` ではなく **`horse_name`(馬名)をキー** に判定する
  (馬番未確定時は馬名しか手がかりがないため。`horse_notes`が既に馬名をキーにしている
  のと同じ考え方)
- **`trainer`(調教師名)フィールドの追加は本フェーズでは行わない**(2026-08-07
  ユーザー承認: 「trainerはbacklog記載のみ。DB変更が絡むものは次フェーズ」)。
  PDFからは調教師名を取得できるが、今回は捨てるか一時変数に留め、entriesには保存しない。
  次フェーズで`entries`に`trainer`フィールドを追加する際に改めて着手する
  (JSON拡張のためDBマイグレーション自体は不要だが、影響範囲確認のため段階を分ける)

**③ マージロジック: レース行(race_id)は絶対に削除・再作成しない**
`functions/api/races/results-import.js`と同じ「既存レースがあればUPDATE、なければ
INSERT」方式を踏襲する。これにより`prediction_marks`/`prediction_notes`の
`ON DELETE CASCADE`による事故的な予想データ消失を防ぐ。

マージルール(馬名をキーに1頭ずつ突き合わせ):
- 新しい馬名 → entriesに追加
- 既存の馬名で、取り込み側の枠番・馬番が **null** → 何もしない(金曜取込後に木曜の
  データで誤って上書きされるのを防ぐ)
- 既存の馬名で、取り込み側の枠番・馬番が **値あり** → 更新(木→金の確定フローはこれで
  実現する)
- 既存の馬名に **既に確定済みの枠番・馬番があり、取り込み側が別の値** →
  **2026-08-07ユーザー承認: 実運用ではまず発生しないイレギュラーな状態と想定。
  自動上書きはせず、インポート結果画面に警告(例:「◯番はDBでは3番ですが、
  インポートデータでは5番です。競合のため更新していません」)を表示するに留める。
  自動解決・上書きUIは今回のスコープ外**

**④ 予想情報の保護について(制約の共有)**
`prediction_marks`テーブルは`horse_number NOT NULL`かつ
`UNIQUE(race_id, horse_number, user_id)`のため、**馬番が確定するまでそもそも予想印は
付けられない**(UIも数字前提)。一方`horse_notes`(馬メモ)は馬名がキーのため、馬番の
有無に関係なく最初から安全。
→ 上記③のマージ方式(race_id不変・確定済み馬番を無言で上書きしない)により、
「金曜に馬番確定→ユーザーが予想印を付ける→後で同じレースを再インポートしても
予想が消えない」という要件を満たす。「木曜(馬番なし)の時点で予想印を付ける」は
現行アーキテクチャ上不可能なため対象外。

**⑤ UI側の追加対応(2026-08-07ユーザー承認: 本タスクのスコープに含める)**
馬番nullの出走馬が存在できるようになることに伴う安全対策:
- **`public/buy.js`**: entries内に枠番・馬番が未確定(null)の馬が含まれるレースは
  選択・購入できないようガードする(「枠番・馬番が未確定のため購入できません」等の
  案内を表示し、購入UIをブロックする。`entries.length===0`の既存ガードと同様の扱い)
- **`public/prediction.js`**: 枠番・馬番が未確定の馬は、予想印セレクトを無効化する
  (保存できないため)。一覧の並び順は、馬番が無い馬がいる場合は馬名(五十音)順に
  フォールバックする
- **`public/races.js`**: レース一覧カードの出走馬登録状況バッジに、枠番・馬番が
  未確定であることが分かる表示を追加する(例:「出走馬表を編集(18頭・枠番未確定)」)。
  必須ではないが実装コストが低いため合わせて対応する想定

  ActiveX COMコンポーネント。Cloudflare Pages Functions(サーバーレスのJavaScript実行環境)からは
  技術的に呼び出せない。公式ドキュメント上もWindows Serverでの動作は非対応とされている
- **JRA公式サイト(jra.go.jp)への直接アクセス**: 実際にfetchで試したところ、bot対策により
  即座にブロックされることを確認した。利用規約の文言以前に、技術的にアクセスできない
- **netkeiba**: 利用規約でスクレイピングを明示的に禁止している(2024年以降Bot対策も強化)

選択肢(いずれも保留中。方針転換する場合は下記から選ぶ):

- A. 貼り付け方式を磨く方向で進める(現状維持・推奨)
- B. 有料のスクレイピング代行API(Bright Data等)を利用する。技術的には可能だが月額コストが発生し、
  対象サイトの規約違反リスクが完全になくなるわけではない
- C. Windows常時稼働機を別途用意し、JV-Linkを使った中継サーバーを立てる(JRA-VAN公式のため
  規約面は最もクリーンだが、インフラ運用の手間が大きい)

**2026-08-07補足**: クラスタ12(出走馬一覧PDFインポート)は、上記A(貼り付け/ユーザー
手動保存PDFの解析方式)の延長で対応する。JRAサイトへの自動アクセスは行わない(ユーザーが
手動で保存したPDFファイルをアップロードしてもらう方式のため、この調査結果の結論と矛盾しない)。

## 馬券かご 確定仕様(2026-08-01)

目的: 複数レース・複数式別にまたがる買い目を、都度保存せずに一時的にためておき、
最後にまとめて保存する。netkeiba・楽天競馬の「馬券かご」相当。

確定した仕様:

- 対象範囲は「レースをまたいでよい」。複数レース・複数式別の買い目を1つのかごに貯められる
- 現行の「式別を選んで組み合わせ選択→即保存」という都度保存の購入フローは廃止し、
  「かごに追加」→(必要なだけ繰り返す)→「まとめて購入する」の流れに一本化する
  (1点だけ買いたい場合も、必ずかごを経由する)
- かごの中身はブラウザ/端末を閉じたり、後日開き直しても保持されている必要がある。
  → サーバー保存(下書きテーブル)までは不要と判断し、localStorageに保存する方式とする
    (同一端末・同一ブラウザ内でのみ保持され、他の端末とは同期されない想定。複数端末での
    同期が必要になった場合は、サーバー側に下書き用テーブルを追加する改修が別途必要になる)
- 「まとめて購入する」実行時は、かご内の全買い目を1回のAPIリクエストで送信し、サーバー側は
  db.batch()でまとめて書き込む(フェーズ12の教訓を踏まえ、行ごとに個別リクエストを
  ループする実装にはしない)

画面イメージ:

- 購入画面(buy.html)に「かご」パネルを常設(右側 or 下部)。ヘッダー等にも
  「かご: n点 / 合計¥xxx」のように現在の内容を常時表示する
- かご内の各行: 日付・競馬場・レース番号・式別・買い目内容・金額・削除ボタン
- かご下部: 合計点数・合計金額、「まとめて購入する」ボタン、「かごを空にする」ボタン
- 保存成功後はかごを空にし(localStorageもクリア)、購入履歴に反映する

実装時の主な変更点(見積り):

- buy.js: 「購入する」ボタンを「かごに追加」ボタンに置き換え、かご状態(localStorage)の
  読み書き・かごパネルの描画・合計計算を追加。レース遷移時もかごの内容を保持する
- functions/api/tickets/bulk.js(または同等の一括保存API): 複数レース・複数式別が混在した
  買い目配列を受け取れるよう、リクエスト形式を拡張(現状は1レース分の想定になっていないか要確認)
- 将来の複数ユーザー対応(下記)と組み合わせる場合、localStorageのキーをログインユーザーごとに
  分ける(同じ端末を家族で共用した際にかごが混ざらないようにする)配慮が必要
