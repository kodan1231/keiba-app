# CSS / JS のキャッシュ対策

`public/_headers`(Cloudflare Pages のレスポンスヘッダー設定ファイル)で、`/*.css` と
`/*.js` に `Cache-Control: no-cache` を付与する。これはブラウザにキャッシュ自体はさせるが、
**使う前に必ずサーバーへ再検証させる**指定で、変更が無ければ 304(数百バイト)が即返るため
実質コストは小さく、`style.css` や各 `*.js` を変更・デプロイしたら次回読み込みで確実に反映される。

HTML からは `<link rel="stylesheet" href="style.css">` / `<script src="xxx.js">` の形で
**クエリパラメータを付けずに**参照する。CSSやJSを変更しても HTML 側の編集は不要。

> 2026-09-08 以前は全 HTML で `style.css?v=YYYYMMDDHHmm`(実際には `v=1`, `v=2`, ... の
> 連番)という手動キャッシュバスティングを行っていたが、更新漏れで反映されない事故が
> 起きやすいため `_headers` 方式へ移行し、全 HTML から `?v=` を除去した。`?v=` は復活させない。

## DBマイグレーションの運用(node不要・wranglerコマンドのみで手動運用)

`migration.sql`には**まだ本番へ適用していないスキーマ変更のみ**を、`-- @STEP: 名前`
ブロックとして末尾に追記していく。各ブロックが適用済みかどうかは、DB自身に作成される
`schema_migrations`テーブルに記録する(名前をキーに1行1件)。

適用手順(手動・wranglerのみ):

1. `migration.sql`に新しい`-- @STEP: 名前`ブロックを追記する
2. そのブロックのSQLだけを一時ファイルにコピーし、まず`--local`で試してから`--remote`
   (本番)に適用する
3. 成功したら`schema_migrations`に`INSERT INTO schema_migrations (name) VALUES
   ('ステップ名');`で記録する
4. `migration.sql`から該当ブロックを削除し、内容を`schema.sql`へ反映する(新規DBでも最初から
   最新構造になるように)。これにより`migration.sql`は常に「これから適用すべき差分だけ」を
   保持する軽量な状態を保つ

DROP/RENAMEを伴う破壊的な変更は極力避け、`ALTER TABLE ADD COLUMN`や`CREATE TABLE/INDEX
IF NOT EXISTS`など、途中で失敗しても安全な内容にすること。途中で失敗した場合は
`PRAGMA table_info`等で実際にどこまで反映されているかを確認してから、schema_migrationsへの
記録や残りのSQLを個別に対応する。`DROP`/`RENAME`を伴う変更は再実行すると
データを壊す恐れがあるため、特に慎重に確認すること。

**「本番は既に運用中でユーザーの実データが入っている」という前提に基づく破壊的変更回避
ルール**: `DROP TABLE`・`DELETE`・既存データを上書きする`UPDATE`など、データやテーブルを
削除・巻き戻す可能性のある変更は極力行わない。追加的な変更(`ALTER TABLE ADD COLUMN`、
`CREATE TABLE/INDEX IF NOT EXISTS`)を基本とし、どうしても削除的な変更が必要な場合は、
影響範囲を明示した上で作業前に必ずユーザーの承認を得ること。なお、出走馬一覧PDFインポート
機能の`horse_number`のnullable化は、`entries`がスキーマレスなJSON列であるため、
そもそもこのマイグレーション手順の対象外(DDL変更不要)である。

更新後に再デプロイします。

```bash
npx wrangler pages deploy public --project-name=keiba-yosou-app
```

> 注意: `migration.sql` は既存DBを最新版へ更新するためのものです。新規DBは `schema.sql` を使用してください。
> 既存DBに複数ユーザー対応のマイグレーションを適用した場合は、管理者アカウント作成後に
> `archive/migrations/assign_existing_data_to_admin.sql` を1回実行して、既存データを管理者アカウントに割り当ててください
> (README「複数ユーザー対応について」参照)。

## DBファイルの役割

- `schema.sql`: 新規DBを最新版で構築するための最終スキーマ。新規構築時に1回実行する
- `migration.sql`: 既存DBを最新版へ更新するための統合マイグレーション。**未適用の`-- @STEP`
  ブロックのみ**を保持する(適用済みの内容は`schema.sql`に反映し、ファイルからは削除する)
- `archive/migrations/`: 過去の番号付きmigration・過去の`migration.sql`(旧`latest1.sql`)の
  アーカイブ・単発マイグレーションファイルの履歴保管場所。通常のセットアップ・更新では使用しない
- `archive/scripts/migrate.js`: 以前使用していた自動適用ラッパー(廃止済み・履歴保管のみ。
  旧ファイル名`latest1.sql`を参照するコードのまま保管している)

新しいスキーマ変更を行う場合は、`schema.sql`と`migration.sql`の両方を更新し、このファイル
(`docs/design/ops.md`)の該当箇所も合わせて更新してください。

## 重い機能の自動一時停止(2026-10-08〜)

D1 の使用量(読み取り・書き込みそれぞれの割合。アカウント全体)がしきい値を超えたら、選んだ重い機能だけを一時停止する
(`functions/api/_lib/service-guard.js`。`functions/_middleware.js` から判定)。購入・履歴・予想などの普段の操作は止めない。
止めた機能へのリクエストは 503(`X-Service-Guard: 1`)を返し、画面の下に「ただいま混雑のため、この機能を一時的に停止しています。
時間をおいてお試しください。」と数秒だけ出す(`public/auth.js` の `showServiceGuardNotice`。不安を与えないよう短い文にする)。

- **2026-11-02 変更(ユーザー要望)**: 読み取りと書き込みで、しきい値と止める機能を別々に持つ。以前は「読み取り・書き込みの割合の
  大きい方」1つで同じ機能を止めていたため、書き込みが80%を超えても止まるのは読み取りの重い機能(本番の設定では一括補正・全期間表示)
  だけで書き込みは減らず、過去の結果の取り込み(1日に約900レース。`race_results` の INSERT だけで約7.3万行)で書き込みが上限
  (10万行)を超え、全画面が止まった(10/14・10/15・11/01〈UTC〉)。
  - 読み取り: 読み取りの割合 ≥ `thresholdPercent` で `targets` を止める(以前からの設定をそのまま使う)
  - 書き込み: 書き込みの割合 ≥ `writeThresholdPercent`(既定80)で `writeTargets`(既定: 取り込み・一括補正)を止める。
    保存済みの設定に無ければ既定が効く(本番は追加の操作なしで取り込み・一括補正が書き込み80%で止まる)
  - 書き込みで止めたときの案内は「ただいまデータベースへの書き込みが多いため、この機能を一時的に停止しています。日本時間の朝9時以降に
    もう一度お試しください。」(書き込みはその日のうちには減らないため)。取り込みの画面・ユーザースクリプトはこの文をそのまま出す
  - 手動停止は両方の一覧の機能を止める。解除(override)は両方に効く
  - 使用量は5分使い回すので、しきい値を超えてから止まるまでに数分分の書き込みが入る(取り込みの速さで数千行。80%なら上限まで2万行の余裕)
- 設定は管理画面「重い機能の自動一時停止」で変える(`app_settings` の key=`service_guard`。`@STEP: service_guard`):
  - 自動一時停止を使うか / 読み取りのしきい値と止める機能 / 書き込みのしきい値と止める機能(2026-11-02〜)
    (読み取りの既定: データ検索・一括補正・夜間の計算。書き込みの既定: 取り込み・一括補正。どちらもほかの機能を選べる)
  - 使用量に関係なく今すぐ止める(緊急用。選んだ機能を止める)
  - 一時停止を解除(次のリセット〈日本時間9時〉まで自動では止めない)/ 解除をやめる
- 判定は「止める対象の機能」へのリクエストのときだけ行う。設定は1分、使用量は5分、同じ実行環境で使い回す
  (使用量は古ければ古い値ですぐ判定し、裏で取り直す。利用者の操作を待たせないため)。設定の変更・解除の反映は最大1分遅れる。
- `CF_ANALYTICS_TOKEN` が未設定なら使用量による自動停止は働かない(手動停止は働く)。使用量が取れない・判定に失敗したときは止めない。
- 日本時間9時に使用量がリセットされると、自動停止は自然に解ける(使用量が下がるため)。

- 管理画面の並び(2026-11-18。ユーザー指摘「チェックボックスがどこにかかっているかわかりづらい」): チェックボックスと文言を横に並べ、
  読み取り・書き込みをそれぞれ枠で囲み、枠の中に「しきい値 ○% 以上になったら、チェックした機能を止める」とその機能の一覧を置く(`.guard-form`)。

## 夜間の計算の使用量による打ち切り(2026-11-18〜。ユーザー要望・仕様確認済み)

夜間の計算(`scripts/pace-nightly.mjs`)は D1 を API で直接読むため、上の自動一時停止が効かない。そこで処理(換算の比の 2a・比率の1条件・
距離の比の10歩・評価点の既定値)を始める前に、今日の読み取りの見込みを確かめ、**75%**(`NIGHTLY_READ_LIMIT_PERCENT`)以上なら残りを始めずに
次の回(次の定時起動・翌晩)へ回す。計算待ちに残るので失敗にはしない(まとめに「次の回へ N件」と「打ち切り: …」を出す)。

- 見込み = 分析API の今日の読み取り(`_lib/d1-usage.js` の `loadD1Usage`。数分遅れるので10分ごとに取り直す)+ その後にこの実行が読んだ行数。
  トークンは `CF_ANALYTICS_TOKEN`、無ければ `CF_D1_TOKEN`(同じトークン)。取れないときは止めない。
- **日本時間の8時台は判定しない**(9時に使用量がリセットされるため。ユーザー判断)。
- 75% の理由: 昼の画面の重い機能を止める自動一時停止(既定80%)より手前で止め、夜間の計算のせいで利用者の機能が止まらないようにする。
  実績(11/10〜11/17。GitHub Actions の記録「D1 の読み取り」を UTC の日ごとに合計): 1日平均 約58万行(約12%)、
  最大 約158万行(約32%。11/13。手動の「今すぐ計算」13回を含む)。1回の実行の最大は約37万行(約7%)。普段の日は打ち切りにならない。

## JS・CSS の版付け(2026-11-18〜。ユーザー要望・仕様確認済み)

以前は JS・CSS をすべて `Cache-Control: no-cache`(`public/_headers`)にしており、画面を開くたびに 9〜14 個のファイルについて
「変わったか」をサーバーへ確かめていた(1つずつ Functions の呼び出しにもなる。`_routes.json` が無いため静的ファイルもミドルウェアを通る)。

- `functions/_middleware.js` の `handlePage`: 画面(拡張子なし・`.html`)を返すときに、同じサイトの `<script src>`・`<link href=...css>` に
  `?v=<そのファイルの版>` を付ける。版はファイルの ETag(無ければ中身)の指紋で、同じ実行環境(=同じデプロイ)の中でファイルごとに1回だけ
  `env.ASSETS.fetch` で調べて覚える。
- `?v=` の付いた JS・CSS は `Cache-Control: public, max-age=31536000, immutable`(1年ブラウザに保存)。ファイルを変えると版が変わり URL が変わる。
- 画面(HTML)は書き換えるので、Pages の元の ETag では 304 を返させない(条件付きの見出しを外して読む)。書き換えた後の中身の指紋を ETag にし、
  同じなら 304。元の ETag のまま 304 を返すと、ブラウザが古い版の HTML を使い続けて古い JS を読むため。
- ブックマークレット・ユーザースクリプト・`import("./pace-search.js")` が読むファイル(`?v=` なし)は今までどおり no-cache。
- 書き換えに失敗したときは、版を付けずにそのまま返す。

## D1の上限を超えたときの画面の案内(2026-10-16〜)

**経緯**: D1 の1日の上限(読み取り500万行・書き込み10万行。アカウント全体。日本時間の朝9時に戻る)を超えると、D1 への問い合わせは
すべて断られる(`Your account has exceeded D1's free tier daily row read limit. ... [code: 7500]`)。各APIはばらばらの 500 を返し、
画面は何も出ない・ログイン画面に戻る・ゲストには「公開していません」と出るなどで、利用者には何が起きているか分からなかった。

**仕組み**(`functions/api/_lib/d1-limit.js`・`functions/_middleware.js`・`public/auth.js`):
- ミドルウェアは、API が失敗したとき(500番台〈自動一時停止の 503 は除く〉・例外。データ検索用アプリのゲストの 401 も。設定が読めずに
  「無効」と判定されることがあるため)だけ、`SELECT 1`(読み取り0行。同じ実行環境で30秒使い回す)で D1 が上限で断っているかを確かめる。
  上限なら `503` + `X-D1-Limit: 1` + `{ error: 案内文, d1_limit: true, retry_at }` に置き換える。成功した応答では何もしない。
- 案内文は「ただいまデータベースの1日の利用上限に達したため、データを表示・保存できません。明日(10月17日)の朝9時以降にもう一度
  アクセスしてください。」(日本時間の0時〜9時は「今日」)。
- 画面(`authedFetch`)はこの応答を受けたら、画面の上に案内を固定で出す(閉じるまで出し続ける)。ログインの確認(`/api/auth/check`)が
  この応答のときは、ログイン画面の代わりに案内だけを出す(ログインしても使えないため)。

### 戻し方

1. Actions の backup の実行結果から `keiba-backup-YYYYMMDD` をダウンロードして展開(zip の中に `.tar.gz.enc`)。
2. 復号: `openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in keiba-backup-YYYYMMDD.tar.gz.enc | tar xzf -`(合言葉を聞かれる。Git Bash で可)。
   `backup-out/<表>.json`(`{ table, columns, rows }`)と `_summary.json`(件数)ができる。
3. INSERT 文にする: `node scripts/backup-restore-sql.mjs backup-out/tickets.json [--where user_id=2] > restore.sql`
   (`INSERT OR REPLACE`。同じ主キーの行は置き換え)。
4. 中身と件数を確かめてから `npx wrangler d1 execute keiba-yosou-db --remote --file restore.sql`。
   - 書き込みは行数ぶん(1日の上限10万行)。大きい表は日を分ける。
   - 外部キーがあるので users → tickets 等の順に流す。tickets 等の race_id は今の races を指す(races は消して作り直さないので同じ ID のまま)。
