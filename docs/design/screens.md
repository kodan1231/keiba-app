# 画面仕様

### 全画面共通シェル(`public/shell.js`)

6つのHTML(`index.html`・`history.html`・`prediction.html`・`stats.html`・`races.html`・
`admin.html`)に共通する **ログイン画面(`#login-screen`)** と **ヘッダー(`header.masthead`。
タイトル・ナビ・ユーザー名・かごバッジ・退場ボタン)** のマークアップは、`public/shell.js` が
実行時に生成して注入する。各HTMLが持つのは以下の空の受け皿だけ:

```html
<body data-page="stats">                              <!-- ナビのactive判定に使う -->
<div id="login-screen" class="screen" hidden></div>   <!-- 空。中身はshell.jsが生成 -->
<div id="app-screen" class="screen" hidden>
  <header class="masthead"></header>                  <!-- 空。中身はshell.jsが生成 -->
  <main> ... ページ本体 ... </main>
</div>
```

- `shell.js` は各HTMLで **`utils.js` の直後・`auth.js` より前** に読み込む。`auth.js` が
  `#login-username` 等・`[data-admin-only]` 要素を参照するため、それらが生成済みである必要がある
- ナビ項目は `shell.js` の `NAV_ITEMS` 配列で一元管理。`adminOnly: true` の項目には
  `data-admin-only hidden` が付き、`auth.js` の `applyAdminVisibility()` が表示を切り替える
- ページ固有のヘッダーアクションボタン(`history` の「CSVインポート」、`races` の
  「出走馬一覧PDFをインポート」「JRAレース結果PDFをインポート」「＋ レースを登録」)は
  `shell.js` の `PAGE_ACTIONS` で `data-page` 別に定義。ボタンのidは従来通りで、
  イベント登録は各ページのJS(`app.js`・`races.js`等)が実行時に `getElementById` で行う
- すでに中身が入っている受け皿は上書きしない(段階的移行の安全策)
- `<head>`(フォント・`style.css`)は各HTMLに残す(FOUC回避)。キャッシュ制御は
  `public/_headers` の `Cache-Control: no-cache` で行い、`?v=` クエリは付けない
  (2026-09-08 移行。`docs/design/ops.md`「CSS / JS のキャッシュ対策」参照)

### トップページ(`/`)の表示について

各画面はログイン成功後に別ページへ自動遷移する仕組みを持たない(そのページ内でログイン画面
→アプリ画面に切り替わるだけ)。そのため「ログイン後の初期画面」は実質的に**サイトのルート
URL(`/`)へアクセスした際にどのファイルが表示されるか**で決まる。

対応方式は**ファイル名リネーム**で実現している: 元々「購入履歴」画面だった`index.html`を
`history.html`にリネームし、元々「馬券購入」画面だった`buy.html`を`index.html`にリネームした。
これにより、Cloudflare Pagesの標準挙動(「/」には`index.html`を返す)がそのまま働き、追加の
リダイレクト処理は不要になっている。

**この方式を採った理由**: 当初は`functions/_middleware.js`でルートURL(`/`)を`/buy.html`へ
302リダイレクトする方式を試みたが、Cloudflare Pagesには「`*.html`付きURLへのアクセスを
拡張子なしURLへ自動的に308リダイレクトする」という別の標準挙動があり、この2つが衝突して
意図しないリダイレクトの連鎖(`/index.html` → `/` → `/buy.html` → `/buy`)が発生し、
「馬券履歴」ナビリンクをクリックしても馬券購入画面に遷移してしまう不具合が生じていた。
ファイル名リネーム方式はこの衝突自体を発生させないため、恒久対応として採用している。

### モーダル/ダイアログ共通挙動

出走馬編集(`race-entries-modal`)・払戻編集(`race-payout-modal`)・出走馬一覧PDFインポート
(`jra-entries-import-modal`)・JRAレース結果PDFインポート(`jra-result-import-modal`)(以上
いずれも`races.html`)、および馬券購入モーダル(`purchase-modal`。`index.html`)は、
**ESCキー押下時に「キャンセル」ボタンと同じ扱いで(保存・送信を一切行わず)閉じる**。

- 実装は`public/utils.js`の共通ヘルパー`registerEscToClose(modalEl, closeFn)`を、各画面の
  モーダル初期化コードから呼び出す方式(`public/races.js`・`public/jra-entries-pdf.js`・
  `public/jra-result-pdf.js`・`public/buy.js`)。`closeFn`にはそのモーダルの既存の
  「キャンセル/閉じる」ボタンが呼んでいる処理(モーダルを`hidden`にするだけの関数)を
  そのまま渡しており、独自の確認ダイアログ等は挟まない
- モーダルが表示中(`hidden`でない)の場合のみ閉じる。複数モーダルが同時に開いていても、
  実際に表示中のものだけが閉じる(通常のUIフロー上、複数モーダル同時オープンは想定していないが、
  安全側の設計としている)
- フォーム入力中でも、送信中でも、確認ダイアログなしにキャンセル相当の挙動で即座に閉じる
  (保存済みデータには影響しない。あくまで未保存の入力を破棄してモーダルを閉じるだけ)

### 購入履歴画面(`history.html`)

常にカレンダーを表示し、画面を開いた直後から**当日が選択済み**の状態になっている(必ず
どこかの日付が選択されている状態を保つ方針。選択解除機能は持たない)。カレンダーの下に
サマリー(選択中の日付の合計。総購入・総払戻・収支・回収率)を表示する(`stats.html`の
「総合成績」(全期間集計)とは異なる、その日単独の集計)。カレンダー日別マス目の収支表示は
実数(`toLocaleString()`、例: `+12,345`)で表示する。選択日の履歴はレース単位
(`groupByRace`)にまとめて表示し、日付降順・同日内は競馬場名(ロケール比較)・レース番号の
昇順でソートする。購入履歴の削除成功時は`alert()`を出さず、削除直後に`loadTickets()`で
即座に一覧へ反映する(失敗時のエラーメッセージは`alert()`で表示する)。「今日」ボタンは
表示月を当月に切り替え、今日の日付を選択状態にして履歴も絞り込む。PC(幅`700px`超)では
CSVインポートボタンを表示し、それ以下では非表示にする(機能・APIは維持したまま表示のみ制御)。

#### 履歴の一括削除(選択モード)

- 「◯◯の履歴を表示中」ラベルの右にある小さめの「選択削除」ボタン
  (`#history-select-btn`。`history.html` の `#history-filter-row` 内)で**選択モード**を
  ON/OFF する。ON中はボタン文言が「やめる」・`.active`(赤)になる。
  下部の固定アクションバー(`#bulk-action-bar`)は選択モード中のみ表示する
  (`#bulk-action-bar[hidden]{display:none}` を明示。id セレクタの `display:flex` が
  `[hidden]` に勝つため)。
- **対象は通常購入(`tickets`)のみ**。CSV取込分(`imported_ticket_items` / レガシー
  `imported_tickets`)にはチェックボックスを出さない(CSV取込は一括削除も行ごと削除もしない)。
- 選択モード中の表示・操作:
  - 一覧の先頭に操作説明(`.bulk-hint`)を表示する。
  - **全レースカードを開いた状態**にする(`renderRaceCard` は `selectionMode` なら常に
    展開)。開閉矢印(`.expand-arrow`)は出さない。購入方式グループの明細は開かない。
  - **見出し行(レースカード / 購入方式グループカードのヘッダー)全体がタップ対象**
    (`.bulk-selectable`)。チェックボックス自体は見た目だけ(`pointer-events:none`)で、
    トグルは見出しのクリックハンドラが行う。
    - グループ見出しのタップ = そのグループの全買い目(`tickets.id`)を選択 ⇔ 全解除。
    - レース見出しのタップ = そのレース内の通常購入の全 `tickets.id` を選択 ⇔ 全解除。
      子グループの選択状況に応じて `checked` / `indeterminate`(部分選択)と
      `.bulk-selected` / `.bulk-partial`(背景ハイライト)を反映する。
  - CSV取込のみのグループ/レースには `.bulk-selectable` を付けず、タップしても何も起きない。
  - 行内の購入額編集input・行ごとの「×」削除ボタン・「払戻を編集(レース管理へ)」リンクは
    CSSで非表示にする(`body.history-selection-mode`。誤操作防止)。
  - 画面下部に固定アクションバー(`#bulk-action-bar`)。未選択時は「タップして購入を選択」、
    選択後は「選択中 N 点」/ キャンセル / 削除する。
  - モバイル(`600px`以下)ではレース見出しの2行化(矢印を行末へ送るための `order` 調整)を
    選択モード時だけ素直な1〜2行フローへ戻す(矢印が無いため)。
- 選択(`selectedTicketIds`)は**再描画をまたいで保持しない**。日付切り替え・削除後の再読込
  (`applyHistoryFilter()`)で必ずクリアし、チェック状態は `syncBulkSelectionUi()` が付け直す。
- 「削除する」→ `confirm()`(`N 件の買い目を削除します。元に戻せません。`)→
  `POST /api/tickets/bulk-delete`(`{ ids: number[] }`)→ 選択モード解除 → `loadTickets()` で再描画。
- **着順・払戻には触れないため、サーバ側でも `recomputeTicketPayoutsForRace(s)` は呼ばない**
  (購入履歴の削除は `races` / `race_results` および他ユーザーの `tickets.payout` に影響しない)。
  `bulk-delete` は `DELETE FROM tickets WHERE user_id = ? AND id IN (...)` を `db.batch()` で
  実行(id は100件ずつチャンク)。

#### レースカードの表示(モバイルのみ2行化)

- **PC(`700px`超)**: レースカードのヘッダーは1行で、左側に「開閉矢印・日付・競馬場・
  レース番号・レース名」を配置し、右側に「購入額・払戻額・収支」を配置する。レース名は
  従来通り省略せず全文表示する(画面幅に余裕があるため)。
- **モバイル(`700px`以下)**: 縦に長くなりすぎるのを防ぐため、ヘッダーを次の2行構成にする。
  - **1行目**: 競馬場・レース番号・レース名。**日付は表示しない**(購入履歴画面は
    カレンダーで日付を選択したうえで一覧を表示する仕組みのため、選択済みの日付を
    レースカードにも重複表示する必要がないと判断した)。レース名は画面幅に収まらない
    場合のみCSSの`text-overflow: ellipsis`で省略する(固定文字数でのカットではなく、
    実際の描画幅に応じて可変)
  - **2行目**: 「購入額 / 払戻額 / 収支」を**左寄せ**で表示し、**行末に開閉矢印(▸/▾)**を
    表示する(PCでは矢印は1行目の先頭にあるが、モバイルのみ2行目の末尾へ移動する)
  - 払戻額・収支の表示条件(確定済みチケットが1件以上ある場合のみ表示)は変更しない
- **確定状況バッジ(未確定/一部確定/確定済み)はレース単位でのみ表示する**
  (`.race-total`の先頭。`ticketGroupStatus(race.tickets)`。2026-09-17)。
  同一レースの着順・払戻は式別・買い目を問わず一括で確定するため
  (`recomputeTicketPayoutsForRace`がレース単位で全ユーザーの`tickets.payout`を
  再計算する)、1つのレース内で式別ごとに確定状況が分かれることはない。
  以前は購入方式グループの行(`.group-card-head`)にも個別のバッジを出していたが、
  意味のある情報を持たない重複表示だったため削除した。
- **実装方針**: HTML構造自体はPC・モバイル共通(`public/app.js`の`renderRaceCard()`)。
  開閉矢印(`.expand-arrow`)を`.race-card-head-main`の外(`.race-card-head`の直接の子)に
  出したうえで、`public/style.css`の`@media (max-width: 700px)`ブロック内でflexboxの
  `order`・`flex-basis`(`.race-card-head-main { flex: 1 1 100%; }`で1行目を強制的に
  改行させる)・`margin-right: auto`(`.race-total`に指定し、後続の矢印を行末へ押し出す)を
  使って見た目だけを並べ替えている。JS側はDOM構造の変更のみで、開閉ロジック
  (`head.querySelector(".expand-arrow")`によるテキスト切り替え)に変更はない。

#### 購入方式グループのダイアログ(馬券風デザイン。2026-09-16〜)

- レース単位のアコーディオン(`.race-card`)を開いた状態で、購入方式(式別)の行
  (`.group-card-head`。式別バッジ・方式・点数・金額・確定状況を表示)をタップすると、
  **以前はその下に明細をインライン展開していたが**、2026-09-16以降は
  **実物のJRA馬券(印字済みの購入済み馬券)を模した専用デザインのダイアログ
  (`#ticket-dialog-overlay` / `.ticket-dialog` / `.ticket-face`)を開く**方式に変更した。
  デザインは実物の馬券写真を参照して作り込んでおり、シミュレータ画像(webの
  「馬券画像ジェネレーター」)とは異なる実物の仕様(年/回/日の位置、金額の星埋め、
  複数点の列挙形式等)に合わせている。
  - 対象は通常購入・CSV取込グループ(`imported_ticket_items`)の両方(区別しない)。
  - 一括削除の選択モード中(`selectionMode`)は従来通りダイアログを開かず、タップは
    そのグループの通常購入(tickets)を全選択⇔全解除するトグルのまま(変更なし)。

##### 券面(`.ticket-face`)のレイアウト

**縦横比は`aspect-ratio: 750/520`で固定し、買い目の点数が多くても券面自体は
広がらない**(買い目エリア`.ticket-selection-area`だけが`flex:1`+
`overflow-y:auto`で内部スクロールする)。背景は薄緑の縦ストライプ
(`repeating-linear-gradient`)。他社ツール(参考にした「馬券画像ジェネレーター」)の
「YAD」透かしロゴは模倣しない。QRコード・管理番号相当のバーコード数字列は
実データを持てず無意味なダミー表示になるため実装しない。

**`.ticket-face-main`をCSS Gridで2行×3列に組み、実物の「縦帯・買い目の下に
合計欄が続く」配置を正確に再現している**(2026-09-17。以前はflexで
「左情報/縦帯/買い目+合計」を横に3分割していたため、合計欄が縦帯の右側
(買い目列の中)に収まってしまい、実物の「合計欄の左端が縦帯の左端と揃う」
配置と違っていた)。列は`grid-template-columns: 28% 52px 1fr`(左情報列/
縦帯/買い目列)、行は`grid-template-rows: minmax(0, 1fr) auto`(1行目=左情報・
縦帯・買い目、2行目=合計欄)。**縦帯(2列目)の中心が券面中央よりやや左に来るよう
左情報列を33%→28%にしている**(実物は縦帯が中央よりやや左寄りに見えるため。
2026-09-18に33%→28%へ5ポイント縮小し、縦帯をさらに左へ寄せた。フリー
になった幅は3列目〈買い目列。単勝・複勝の馬名表示幅〉に回る)。
縦帯の幅も56px→52px(約7%)に詰めている(2026-09-18)。上下の英字表記
(最長でQUINELLA/TRIFECTAの8文字・2行)が潰れたり3行に増えたりしない
範囲でできるだけ細くする方針は変わらず(2026-09-17に64px→56pxへ変更した
経緯を継続)、**幅を詰めた分だけ`.ticket-strip-label`の`font-size`
(8.5px→8px)・`letter-spacing`(0.1px→0)・左右`padding`(1px→0px)も
比例して詰め、8文字が1行に収まる余裕(3行に増えない)を維持している**。

  「年/回/日・場名・R番号」が列の上側に、「レース名・発売場・月日」が下側に
  分かれ、間(QRコードがある位置)が空いている。上側ブロック(`.ticket-info-top`)は
  通常のフローで列の先頭に配置し、下側ブロック(`.ticket-info-bottom`)は
  合計欄(`.ticket-face-footer`)の下端と揃えるため`position:absolute; left:0;

  直接固定している(2026-09-18)。**以前は`.ticket-info-col`の`grid-row`を
  合計欄の行(2行目)までまたがせ、`justify-content:space-between`で下側
  ブロックを押し下げる方式だったが、その方式だと下側ブロックの分だけ
  合計欄の行(`auto`)の必要高さが増え、その分1行目(`minmax(0,1fr)`。買い目列

  - `.ticket-info-top`: 上から`.ticket-year-line`(開催年。`font-size:23px`)・

    JRA表記の「回・日」(例: 2024年3回2日)は`tickets.kai`/`tickets.nichi`相当の

    削除した。日付自体は下ブロックの月日で区別できる)。
  - `.ticket-info-bottom`: 上から レース名(`.ticket-face-race-name`。
    `ticketShouldShowRaceName()`が`true`の場合のみ表示。**先頭が「障害」、または

    レース名欄に印字されるため、判定は`race_name`の先頭パターンのみで行う)・

  単勝=WIN、複勝=PLACE/SHOW、枠連=BRACKET QUINELLA、馬連=QUINELLA、
  ワイド=QUINELLA/PLACE、馬単=EXACTA、三連複=TRIO、三連単=TRIFECTA)を表示し、
  中央に式別名(`ticketBetTypeText()`。三連複・三連単だけは実物同様「三」ではなく
  算用数字の「3連複」「3連単」にする)を**1文字ずつ`<span>`で縦に積んで**表示する

##### 購入方式の入力構造(tickets.structure)による正確な表示(2026-09-17〜)

上記の通り、保存済みの`selections`(実際に生成された組み合わせ結果)からの逆算
(`describeGroupSelections()`)だけでは、着順なし券種のフォーメーションのゾーン
分けが復元不可能という制約があった。**過去の購入データ・CSV取込データはこの
制約を許容する(遡及対応はしない)方針とし、今後の画面購入(カゴ経由)分のみ、
購入モーダルが入力時点で保持している構造情報を`tickets.structure`にそのまま
保存し、表示側はそれを最優先で使う**ようにした。

- 保存元は`public/buy-purchase-modal.js`の`buildCurrentStructure()`。
  `public/cart.js`(カート・`checkout()`)を経由して`POST /api/tickets/bulk`の
  グループペイロードに含まれ、`functions/api/tickets/bulk.js`が同一`group_id`の
  全チケット行に同じ`structure`(JSON文字列)を保存する。`GET /api/tickets`
  (`functions/api/tickets/index.js`)は`selections`と同様にJSON.parseして返す。
  JSON形式・method別の詳細は`docs/design/data-model.md`
  「購入方式の入力構造(tickets.structure)」参照。
- `describeGroupSelections()`(`ticket-view.js`)は`group[0].structure`があれば
  最優先で使い(box→馬番一覧、nagashi→軸/相手、formation→着順ごとの集合を
  そのまま`slots`から返す)、無ければ従来の推測ロジック(交差判定・着順ごとの
  集合比較)にフォールバックする。この関数は履歴画面(本項)・予想登録画面の
  購入済み馬券表示の両方から使われる共通部品のため、この優先順位の変更は
  両画面に等しく効く。
- `ticketMethodBoxLabel()`(`app.js`。本項の「方式ボックス」参照)も同様に
  `structure`があれば優先する。
- **2行目・合計欄(`.ticket-face-footer`。`grid-column: 2/4; grid-row: 2`)**:
  縦帯(2列目)と買い目列(3列目)にまたがって配置することで、**左端が縦帯の
  左端に揃う**(実物の配置に合わせた。買い目列の中に収めていた旧実装では
  縦帯の右合わせになっていた)。中身は`.ticket-totals`。「合計」+星埋め済みの
  枚数・金額(`ticketSheetCountText()`+`ticketTotalAmountHtml()`)**のみ**。
  **払戻・確定状況は券面に表示しない**(2026-09-17に削除。実物の馬券は購入時に
  印字される券面であり、払戻情報は載らないため。履歴としての払戻確認は
  「金額変更」パネル内の明細行(`.detail-payout`)で行う)。

`.ticket-dialog`は以前`overflow: visible;`を指定していたが、これが親の
`.modal`が持つ`overflow-y: auto; max-height: 90vh;`を上書きしてしまい、
「金額変更」パネルを開いて中身が画面高さを超えても**スクロールできず
下の方の明細行が操作できない**不具合になっていた(`overflow`はショートハンドで
`overflow-x`/`overflow-y`両方に効くため)。`.ticket-dialog`から`overflow`指定を
削除し、`.modal`側のスクロール設定をそのまま活かすよう修正した(2026-09-17)。

`.ticket-face-main`のgrid行は`grid-template-rows: minmax(0, 1fr) auto;`にしている
(`1fr`単体ではなく`minmax(0, 1fr)`にすることで、行内の最小コンテンツサイズを
明示的にゼロにしている。`aspect-ratio`と`flex`・`grid`を組み合わせた場合に
高さ計算が不安定になるブラウザ差異への対策。2026-09-17)。同じ理由で
1行目のgrid item(`.ticket-info-col`・`.ticket-strip`・`.ticket-buy-col`)には
`height: 100%`を明示している(grid の`align-items:stretch`だけに頼ると、
これらの中にある`display:flex`コンテナの高さが環境によって行の高さまで
伸びず、`.ticket-info-col`内の`justify-content:space-between`が効かずに
下ブロックが下端に届かない、という不具合が実機で報告されたための対策)。

##### 金額の表記(実物の馬券に合わせた独自フォーマット)

- 券面内の金額は`formatYen()`(¥表記。アプリの他画面で共通)ではなく、
  **末尾に「円」を付ける`ticketYenText()`**を使う(実物の馬券が「¥」ではなく
  「円」表記のため。券面デザイン以外の箇所は従来通り`formatYen()`のまま)。
- 実物の馬券は金額欄の桁数が固定で、空いている上位の桁を星(☆/★)で埋めて
  印字される(内訳行は☆・合計欄は★)。`ticketStarPad(amount, maxDigits, star)`が
  「桁数」から星の数を計算する(**内訳行は最大6桁・合計欄は最大7桁として、
  手元の実物馬券の写真数枚から逆算した推定値**。正確な規則の保証はない)。
  `ticketDetailAmountHtml()`(☆+円)・`ticketTotalAmountHtml()`(★+円)を
  内訳行・合計欄それぞれで使う。
- 実物の馬券は「合計」欄に金額だけでなく**購入枚数(10円単位。100円なら
  10枚)も星埋め付きで表示される**(個別の買い目行には枚数は出ない。合計欄だけの
  表記)。`ticketSheetCountText(amount)`が`Math.round(amount/10)`を計算し、

### レース管理画面(`races.html`。管理者のみ)

購入履歴画面と同様のカレンダーがあり、登録済みレースがある日をマーク、日付をクリックすると
その日のレースだけに絞り込める。特定の日付を選択していない場合は、一覧はカレンダーに
表示中の月のレースだけに絞り込まれる。カレンダーで選択中の日付を再クリックすると絞り込みが
解除され、表示中の月全体の一覧に戻る。

日付選択後の一覧で「未登録」の枠(管理者のみクリック可)をクリックすると、該当する日付・
競馬場・レース番号を事前入力した状態で出走馬表登録モーダルが開く。

レース登録・編集モーダルは「出走馬表」「払戻」の2つに分割されている。レース一覧カードの
操作は、出走馬登録状況バッジ(「出走馬表を登録」/「出走馬表を編集(n頭)」。枠番・馬番が
未確定の馬を含む場合は「(枠番未確定)」のサフィックスが付く)と結果確定状況バッジ
(「払戻を登録」/「払戻を編集」)自体が管理者向けのボタンを兼ね、それぞれ対応するモーダルを
開く。

- 出走馬表モーダル: 開催日・競馬場・R・レース名・コース種別・距離・出走頭数・出走馬
  (テキスト貼り付け一括入力を含む)を扱う。`POST /api/races`または`PUT /api/races/:id`には
  これらのフィールドのみ送信する(着順・払戻は変更しない)
- 払戻モーダル: 既存レースのみが対象。対象レースの日付・競馬場・R等を読み取り専用で
  表示したうえで、着順選択肢の範囲を決める頭数(出走馬表登録済みなら自動設定・未登録時は
  手動選択)・着順(1〜3着)・馬券式別の払戻金額を扱い、`PUT /api/races/:id`には
  `finish_order`・`payouts`のみ送信する(各購入履歴(`tickets.payout`)への反映はサーバー側で
  行うため、`races.js`からticketを直接更新するリクエストは送らない。詳細は下記
  「払戻確定時のticket反映」参照)
- `race_results`(全着順・タイム・馬体重等・「競走中の出来事」)は専用の編集UIを用意せず、
  PDFインポート経由での自動登録のみとし、`incident_note`のみレース管理画面から編集できる
- **開催日程を一括登録する機能は廃止した**(2026-08-30)。新規レースの登録は
  「＋ レースを登録」ボタンから出走馬表モーダルを個別に開いて行う(競馬場が横並びカラムで
  表示され「未登録」の枠をクリックする経路も従来通り利用できる)

`history.html`の「払戻を編集(レース管理へ)」リンク(`races.html?edit=`)は払戻モーダルを
直接開く。モーダルは開くたびにスクロール位置が先頭にリセットされる。払戻入力欄(式別
ブロック・組み合わせ行)はモーダル幅を活かしたグリッドレイアウトで横に並べて表示する。

ヘッダーには「出走馬一覧PDFをインポート」「JRAレース結果PDFをインポート」ボタンがある

### 集計画面(`stats.html`)

タブは「総合成績 / レース別 / 競馬場別 / コース別 / 騎手別」。

**レース区分フィルタ(総合成績・レース別。2026-09-19追加)**: この2タブにはそれぞれ
独立した「すべて/重賞のみ/条件戦のみ」フィルタがある(`競馬場別`/`コース別`/`騎手別`には無い)。
分類ロジック・重賞マスタ管理の詳細は `docs/design/graded-races.md` 参照。フィルタ切替は
全購入データを再フェッチせずクライアント側で絞り込むだけ(`public/stats.js`の
`categoryFilterState`/`filterByCategory()`)。

**総合成績タブ**: サマリーカード(総購入・総払戻・収支・回収率・的中率)の下に、購入金額の
比率を示す棒グラフを3種類表示する(`renderRatioBreakdowns()`)。分母はいずれも「全購入の
合計金額(未確定を含む)」、バーの幅は比率(%)そのもの。値表示は「比率% / ¥金額」
(スマホ幅では ¥金額を隠す)。

- **馬券種別別 購入比率**: `bet_type` ごとに購入金額を合算。`BET_TYPES` の定義順で並べ、
  定義外の `bet_type`(不明等)は末尾。
- **競馬場別 購入比率**: `track` ごとに合算。金額の多い順。`track` 空欄は「競馬場不明」。
- **騎手別 購入比率**: 1枚の馬券に複数騎手が絡む場合は各騎手へ**全額**を計上する
  (按分しない。「騎手別収支」表と同じ方針)。そのためバーの合計は 100% を超えることが
  ある(注記あり)。金額の多い順に上位10名を表示し、残りは「その他(N名)」1本に集約する。
  騎手情報を持たない購入(CSV取込分など)は計上されない。

レース別・競馬場別・コース別・騎手別の4表とも、
列見出し(購入/払戻/収支/回収率/的中率、および先頭列)をクリックすると、その列で
昇順⇔降順を切り替えられる。初期表示のソート順:

- レース別: 日付・競馬場・レース番号の順(3つを連結したキーで比較。日付が新しい順)
- 競馬場別: 購入金額の多い順
- コース別: 購入金額の多い順(先頭列でソートすると「競馬場→芝/ダート/障害→距離昇順」の
  並びになる。表示名とは別に padding 済みの `sortKey` で比較しているため)
- 騎手別: 回収率の高い順(回収率が未確定(null)の行はソート方向によらず常に末尾)

**競馬場別収支(2026-09-24追加)**: `track` のみでまとめる(コース種別・距離では
分けない)。`track` が空欄の購入は「競馬場不明」に集約する。総合成績タブの
「競馬場別 購入比率」棒グラフと同じ粒度・同じフォールバック文言に揃えている。

**コース別収支**: 「競馬場 × コース種別(芝/ダート/障害) × 距離(正確な m 値)」で1行にまとめる
(例: 「東京 芝1600m」「中山 ダ1200m」「中山 障3000m」。ラベルは `formatCourseText()`)。
レースに `course_type` が登録されていない購入は「(競馬場) コース未登録」に集約する
フォールバック。`course_type` はあるが `distance` が無い場合は距離を省いて「(競馬場) 芝」等。
コース種別・距離は `GET /api/tickets`(`race_course_type` / `race_distance` をレースJOINで付与)
および `GET /api/ticket-imports`(`races` を全件1回SELECTしてメモリ照合)が返す。
レガシー取込(`race_id` 無し)は常に「コース未登録」側になる。

数値列(購入/払戻/収支/回収率/的中率)は初回クリックで降順、文字列・日付列(先頭列)は
初回クリックで昇順から始まる。値がnull(未確定で回収率・的中率が算出できない行)は
ソート方向によらず常に末尾に表示する。

**馬名ベース・騎手名ベースの成績集計(`race_results`を使った過去出走一覧・的中率等)は
今回のスコープに含まない(BACKLOG「クラスタM」参照)。**

### 馬券かご機能(2026-09-06〜)

複数レース・複数式別の買い目を一時的にためておき、まとめて購入する機能。以前の
「式別を選んで組み合わせ選択→即保存」という都度保存フローは廃止し、「かごに追加」→
「まとめて購入する」の流れに一本化した(1点だけ買う場合もかごを経由する)。旧設計仕様は
`docs/ROADMAP.md`の旧クラスタFに記載していたが、実装完了に伴い本節へ実装内容を反映し、
ROADMAP.md側からは削除した。

- **保存先**: サーバー保存ではなく`localStorage`(`public/cart.js`)。キーは
  `keiba-cart:<username>`でユーザーごとに分離する(同一端末を家族で共用しても混ざらない)。
  他端末・他ブラウザとは同期されない
- **UI**: 全画面共通ヘッダーの「かご」ボタン(バッジに選択中の点数を表示。**選択中の
  点数が0のときは赤丸バッジ自体を非表示**)から`public/cart.js`が動的生成するパネルを
  開く。グループ(かごに追加した1回の操作)単位で開閉・一括金額変更・個別チェックの
  ON/OFFができる。バッジ用CSS(`.cart-badge-count`)は`cart.js`が注入するが、
  `display: inline-flex`が`hidden`属性を上書きしてしまうため`.cart-badge-count[hidden]
  { display: none }`も併せて注入して打ち消している
- **購入確定**: パネルの「購入」ボタンから`POST /api/tickets/bulk`
  (`functions/api/tickets/bulk.js`)を1回だけ呼び出し、チェック済みの全グループ・
  全買い目をまとめて送信する。サーバー側は対象レースを1回のSELECT(IN句)でまとめて
  取得し、`db.batch()`で一括INSERTする(サブリクエスト数対策。他のPDFインポート・
  CSVインポートと同じ方針)
- **リクエスト形式(破壊的変更)**: 以前は1レース・1式別分の`combos`配列のみを受け付ける
  単一グループ形式だったが、`{ groups: [{ client_key, race_id, race_date, track,
  race_number, race_name, bet_type, method, memo, combos: [...] }, ...] }`という
  複数グループ配列形式へ変更した。呼び出し元は`cart.js`のみのため旧形式との後方互換は
  持たせていない
- **`client_key`による突き合わせ**: カゴ側が任意に付与する相関キー。レスポンスの
  `results[].client_key`と突き合わせ、成功(`created`)したグループの、送信した
  (チェック済みだった)買い目だけをカゴから削除する。未チェックの買い目・失敗した
  グループはカゴに残る
- **結果確定済みレースへの反映**: 購入直後に、対象レースが既に着順・払戻確定済みの
  場合は`recomputeTicketPayoutsForRaces()`(複数レース一括版)を呼び出し即座に払戻を
  反映する(既存の「確定済みレースへの購入時の払戻即時反映」仕様と同じロジックを
  複数レース対応に拡張したもの)
- **未実施**: 実ブラウザ・実DBでの動作検証(`docs/BACKLOG.md`参照)

#### レース選択グリッド(競馬場×R一覧)

`renderGrid()`が、日付選択後に競馬場×R番号のグリッドを描画する(旧仕様はBACKLOG
「クラスタB」参照。②コース情報表示・③カラム幅縮小・④メモありマーク・モバイルタブ化を

- **PC(700px超)**: 従来通り全競馬場を横並びカラムで表示する。カラム最小幅を`200px`に

- **発走時刻の表示(2026-09-13追加)**: `races.post_time`(`"HH:MM"`)が入っている場合、

##### API仕様: `GET /api/horse-notes`(race_id省略時の一覧取得モード)

`functions/api/horse-notes/index.js`の`GET`ハンドラは、クエリパラメータに`race_id`が
**含まれない**場合、従来の「指定レースの出走馬のメモ一覧」モードとは別の「自分の全メモの
うち空でないものの馬名一覧」モードとして動作する。

- リクエスト: `GET /api/horse-notes`(`race_id`パラメータなし)
- レスポンス: `{ "names": ["馬名1", "馬名2", ...] }`(メモ本文は含まない。購入画面での
  「メモの有無」判定にのみ使うため、本文を返す必要が無い)
- 対象はログインユーザー自身の`horse_notes`のみ(`WHERE user_id = ?`)
- 既存の`race_id`指定時の挙動(予想登録画面`prediction.html`での利用)には影響しない

##### API仕様: `GET /api/predictions`(race_id省略時の一覧取得モード)

`functions/api/predictions/index.js`の`GET`ハンドラは、クエリパラメータに`race_id`が
**含まれない**場合、従来の「指定レースの予想印・予想メモ・勝負レースフラグ取得」モードとは
別の「自分が勝負レースに設定済みのレースID一覧取得」モードとして動作する(`GET
/api/horse-notes`のrace_id省略時と同じ考え方)。

- リクエスト: `GET /api/predictions`(`race_id`パラメータなし)
- レスポンス: `{ "race_ids": [1, 5, 12, ...] }`
- 対象はログインユーザー自身の`prediction_notes`のうち`is_key_race = 1`のもののみ
- 既存の`race_id`指定時の挙動(予想登録画面`prediction.html`での利用)には影響しない

##### API仕様: `PUT /api/predictions/key-race`

勝負レースフラグのON/OFF切り替え専用エンドポイント。予想印・予想メモの保存
(`POST /api/predictions`。marks/memoを毎回まとめて上書きする設計)とは独立させている。

- リクエスト: `PUT /api/predictions/key-race` `{ "race_id": 123, "is_key_race": true }`
- `prediction_notes(race_id, user_id)`へUPSERT(`is_key_race`・`updated_at`のみ更新。
  既存のmemo/予想印には影響しない)
- レスポンス: `{ "ok": true, "race_id": 123, "is_key_race": true }`

開催日・レース選択画面(競馬場×R番号のグリッド)では、ログインユーザー自身がそのレースの
馬券を1点以上購入済みのものは、行の背景色(win(緑)系の薄いアクセント、
`.race-column-row.purchased`)で視覚的に区別する。判定対象は通常購入(`tickets`)と
CSVインポート分(`imported_ticket_groups`経由の`imported_ticket_items`)の両方で、
どちらか一方にでも該当する購入履歴があれば購入済みとして扱う。判定は**ログイン中の自分の
購入のみ**を対象とする(他ユーザーの購入は含めない)。

**三連複・三連単の「2頭軸」は、「軸1」「軸2」「相手」(三連単は着順ラベル)の3列**
(2026-09-21。経緯: 当初「軸」(最大2頭までのチェック)・「相手」の2列で実装し、レイアウト
崩れの指摘を受けて一旦「この2列で正しい」とドキュメント化したが、netkeiba実物の
スクリーンショット2枚(三連単マルチON時の「1着軸」「2着軸」「相手」、三連複の
「軸1」「軸2」「相手」)で反証され、両方とも3列に修正した)。

三連単はマルチOFFの場合、軸2頭を具体的にどちらの着順に置くかで馬券そのものが変わる
(例: A→1着・B→2着 と B→1着・A→2着 は別の買い目)。「軸(最大2頭までのチェック)」という
順序を持たない1列では、この着順をチェックした**クリック順**に頼らざるを得ず、画面上に
どちらが1着でどちらが2着かを示す手がかりが無いまま組み合わせが決まってしまう欠陥があった。
三連複には着順の概念が無く「軸1」「軸2」の区別自体は組み合わせ生成上は不要だが、
netkeiba実物が同じ3列构成のため、見た目の一貫性としてこの仕様に合わせた。

- **軸1/軸2(三連単はaxisPlacementで選んだ2つの着順ラベル。例: 1・3着選択時は
  「1着軸」「3着軸」。`axisPositionLabels()`)**: それぞれ単一選択(ラジオボタン、
  `name="axis-pos1"`/`"axis-pos2"`)。片方の列で選んだ馬はもう片方の列では選べない
  (`disabled`)
- **相手**: 複数選択のチェックボックス。軸に選ばれた馬は選択不可

状態は`state.axisOrder = [軸1の馬番, 軸2の馬番]`で保持し(クリック順ではなく列の
意味そのものを保存する)、組み合わせ生成(`currentCombos()`)もこの配列をそのまま
`axis[0]`/`axis[1]`として使う(1頭軸`axisCount===1`は従来通り`axisSet`のまま)。
三連複は`axis[0]`/`axis[1]`の順序が結果に影響しない(`generateCombinations(...,false)`が
順序違いを重複除去する)ため軸1/軸2どちらで選んでも同じ買い目になる。三連単マルチON時も
`generateAxis2Multi()`が軸2頭+相手の全着順(6通り)を生成するため同様にどちらの列で
選んでも最終的な買い目は変わらないが、UI自体はマルチのON/OFFに関わらずnetkeiba実物と
同じ3列のまま統一する(JRA公式の説明でも、2頭軸マルチは「指定した軸馬の組合せの
1着→2着ながし、1着→3着ながし、2着→3着ながしとそれぞれの軸馬の着順を入れ替えた
組合せを同時購入」であり、点数はマルチOFF時の6倍になる)。

表ヘッダー(`.bet-horse-table-head`。列見出しはここにある)はモバイル幅(700px以下)で
非表示になるため、行ごとのチェック/ラジオだけでは意味が分からず「列が足りないのでは」と
誤解されやすい。加えて`.bet-horse-row`/`.bet-horse-control`は通常・BOX・フォーメーション等の
全購入方式で共有されておりブレークポイントごとに何度も上書きされてきた経緯があり、2頭軸の
チェックがiPhone SE3(幅375px)実機で縦に折り返って見える不具合も同時に発生していた。
対応として、2頭軸の行は`.axis2-row.axis2-row-3col`クラスで独立させ、汎用ルールに頼らず
横並びを明示的に固定し、かつ各チェック/ラジオに常時小さなラベル(`.axis2-check-tag`。
PC幅では表ヘッダーの見出しと二重になるため701px以上で非表示)を付けて、見出しが隠れる幅
でも意味が分かるようにした。

出走馬に枠番・馬番が未確定(null)の馬が1頭でも含まれるレースを開いた場合、購入UI自体を
表示せず「このレースは枠番・馬番が未確定のため、購入できません」という案内のみを表示する
(`hasUnconfirmedEntries()`)。

- ヘッダーは**2行構成**(`renderRaceHeader()`)。

    非表示)。**牝馬限定なら「牝」**(`class_flags` の生テキストに「牝」を含む)、
    **ハンデ戦なら「H」**(`weight_type` または `class_flags` に「ハンデ」を含む)を

    (`toggleKeyRace()`)。ユーザーごとの個人設定(`prediction_notes.is_key_race`。
    予想印・予想メモと同じテーブル・粒度)で、他ユーザーには見えない。ONにすると
    馬券購入画面のレース選択グリッドのレース名の後ろにも「★」が表示される

    (`POST /api/predictions`)とは独立した専用エンドポイントのため、印を変更しても
    このフラグは変化せず、このフラグを切り替えても印・メモは変化しない
- **日付セレクトまたは競馬場セレクトを変更したときは、現在のレース番号(R)をできるだけ
  維持する**(`switchToRaceKeeping()`)。優先順は「日付+競馬場+R一致 → 日付+競馬場一致の
  先頭R → その日付の先頭レース」(以前は競馬場変更時に常にその開催の先頭レースへ
  切り替わっていた。日付セレクトは無かった)
- 「このレースの馬券を購入」ボタンの遷移先URLには `?from=prediction` を付け、購入モーダルを
  ×/ESCで閉じたときにこの予想登録画面へ戻れるようにする(「購入画面(`index.html`)」参照)
- 馬一覧を上部、購入済み馬券の一覧を下部に配置する
- 各馬の行は「馬番・馬名・予想印・メモ有無マーク」の4列。馬番は丸背景で表示し、その背景色を
  枠色(`--waku-1`〜`--waku-8`)にすることで枠番を表す(枠番の独立バッジ `.mini-waku` は
  予想画面では廃止)。枠番未確定(`waku_number` が 0/null)の馬は輪郭のみの丸にする
- 行をクリックすると展開パネル(馬メモ + 過去成績)が開閉する。開閉状態を示す「＋/−」
  記号は表示しない(2026-09-10に廃止。行ホバーの背景変化とメモ「▼」マークで開閉可能な
  ことを示す)
- 馬名列は2段組み。1段目に馬名、2段目に「性齢 ・ 負担重量 ・ 騎手名」を「・」区切りで
  小さく1行表示する(はみ出しは `…` で省略、折り返さない)。性齢(`sex_age`)・
  負担重量(`weight_carried`)は出走馬一覧PDFまたはJRAレース結果PDFのインポートでのみ
  入るため、手動登録レースなど値の無い項目は出さない(全部無ければ2段目そのものを出さない)。
  負担重量は `56.0kg` のように小数第1位まで表示する
- 2段組みにしても行の高さは実質変わらない(元々、予想印セレクトの高さで行高が決まっており、
  馬名2段ぶんがその中に収まるため)。馬番・予想印・メモ有無マークは従来どおり行内に1段で表示する
- 各馬のメモの有無は、行末に表示する赤色の「▼」マークで一覧のまま把握できる
  (行を開かなくても分かる)。メモ本文のプレビュー表示や、馬名横の
  個別バッジ、行全体の背景色強調は行わない(表示要素を絞ることで、メモの有無にかかわらず
  行の高さを揃えている)。操作説明文(「予想印は馬名の横で変更できます…」)は表示しない
- **各馬の展開パネルには、馬メモ(上)に続けて「過去成績(出走履歴)」(下)を表示する**。
  出典は `race_results`(JRAレース結果PDF取込済みの馬単位の確定結果)。表示中のレース自身を
  除き、馬名を `horseAliasKeyOf`(NFKC+空白除去)+ `horse_aliases` エイリアスで正規化した
  キーで横断一致させ、**`race_date` 降順で全件** 出す(`docs/design/horse-aliases.md` 参照)。
  `race_results` に一致行が無い馬は従来どおりメモのみ(セクション自体を出さない)。
  取得は `GET /api/races/:id/horse-history`(全ユーザー共有データのためログインのみで可)。
  `selectRace()` が予想印・馬メモの読み込みとは**切り離して**呼び(`loadHorseHistory()`)、
  取得・JSONパースの失敗は握りつぶす(購入馬券欄 `loadRaceTickets()` と同じ考え方。
  この画面の馬メモ表示に巻き添え不具合を出さないため)。列は「日付・場R・コース
  (`formatCourseText`)・着順(`3着 / 16頭`。取消/除外/中止は状態ラベル)・人気・騎手・
  斤量・馬体重(増減)・タイム・着差」で、列が多いため表は横スクロールで見せる
  (`.horse-history-scroll`)。各行の `title` に過去レース名を出す
- 「このレースの購入馬券」欄の通常購入分は、各買い目行の購入金額をその場で編集できる。
  編集時は既存の `PUT /api/tickets/:id` を使用し、入力値は100円以上の100円単位とする。
  払戻率が登録済みの場合は、変更後の購入金額に応じて払戻額も再計算する。CSV取込分は
  この画面から編集しない
- 「このレースの購入馬券」欄(購入方式単位のグループカード)は開閉可能
  (`history.html`購入履歴画面の`.group-card`開閉パターンを流用)。初期状態は全カード
  折りたたみで、ヘッダーをクリックすると個別の買い目明細が展開される。開閉状態は
  レース内で購入方式(`group_id`)ごとに保持され、再描画をまたいでも維持される
  (`expandedTicketGroups`)。折りたたみ時でも、そのグループの購入額・払戻額(確定分)は
  ヘッダーに要約表示される
- 購入履歴画面(`app.js`)と予想登録画面(`prediction.js`)の購入馬券グループ表示は、
  差分の無い純粋関数を`public/ticket-view.js`に共通化している(`groupTicketsByGroupId`・
  `ticketMoneyText`=「購入¥… / 払戻¥…」文字列・`ticketGroupStatus`・`selectionCellHtml`
  =馬名付き買い目セルmarkup)。レンダラ本体とDOMイベント配線は両画面それぞれに残す
  (履歴画面は購入額・払戻の編集/削除/管理者リンク/ステータスバッジを持ち、予想画面は
  通常購入の購入額編集のみで削除・ステータスバッジを持たない、という機能差があるため)。
  予想画面の買い目セルは馬番のみ(`formatSelections`)で、`selectionCellHtml`(馬名付き)は
  現状履歴画面のみが使う
- **購入馬券グループの表示(IPAT風コンパクト表示。2026-09-12追加)**: JRA公式IPATの
  「照会結果詳細」画面は、ボックス/フォーメーション/ながし等で生成される全組み合わせ
  (点)を展開せず、「入力した形」(馬番の一覧・着順ごとの馬番・軸馬/相手)を数行で
  見せている、という利用者からの指摘を受けて導入。グループ展開時、これまでの
  1点ずつの明細(`.group-detail-rows`)の**上に**、コンパクトな要約行を追加した
  (`ticket-view.js`の`describeGroupSelections()`/`groupCompactSummaryHtml()`)。
  - **method文字列(`box`/`nagashi`/`formation`/`import`等)には依存しない**。グループ内
    全チケットの実際の`selections`だけから逆算する。理由: CSV取込グループ
    (`imported_ticket_groups`+`imported_ticket_items`)も`tickets`と同じ「1グループ=
    複数組み合わせ」の構造を持つが、`method`列は常に固定文字列`'import'`で内訳が
    残っていないため。method不問のロジックにすることで、通常購入・CSV取込の両方に
    同じ関数をそのまま適用できる
  - 判定ロジック: ①全チケットに共通して登場する馬番(交差)が1〜(n-1)頭あれば
    「軸馬/相手」形式(軸2頭は`－`で連結。例:「軸馬:04－08」「相手:03,05,06,07,09」)。
    ②着順あり(ordered)の券種で、着順位置ごとの馬番集合が全て同じなら「馬番:…」
    (ボックス)、位置ごとに違うなら着順ごとに個別表示(フォーメーション。
    `selectionLabel()`のラベルを流用)。③いずれにも当てはまらなければ「馬番:…」に丸める。
    全点同額なら「各◯◯円」も添える(バラけていれば添えない。合計額は既存の
    `group-money`表示に任せる)
  - **既知の制約**: 着順なし(unordered)の券種のフォーメーションで、かつ共通の軸馬が
    1頭も無い(各着順グループが完全に別々の馬番)場合は、保存時点で組み合わせが
    馬番昇順に正規化されており元の枠分けを復元できないため、「馬番:全馬番の一覧」に
    丸めるフォールバックになる(取りこぼしが起きたら都度対応する方針)
  - 1点のみのグループ(通常の単発購入)ではコンパクト表示を出さない(元々1行で
    足りるため)
  - コンパクト表示の下に「内訳を見る」トグルボタンを新設し、1点ごとの明細
    (当落・個別金額編集・削除)はデフォルトで隠す(`expandedBreakdowns`
    〈`app.js`〉/`expandedTicketBreakdowns`〈`prediction.js`〉。グループの
    開閉状態〈`expandedGroups`/`expandedTicketGroups`〉とは別に保持)
- 枠番・馬番が未確定(null)の馬は予想印セレクトが無効化される。一覧の並び順は、未確定の
  馬がいる場合は馬名(五十音)順にフォールバックする。「このレースの馬券を購入」ボタンは
  「枠番・馬番未確定(購入不可)」表示に変わる

## 日時表示のタイムゾーン

- D1の`created_at`等(`datetime('now')`で保存される列)はUTCの`"YYYY-MM-DD HH:MM:SS"`形式
  (タイムゾーン情報なし)で保存される。この文字列をそのまま`new Date()`に渡すと、閲覧環境に
  よって表示時刻がずれる可能性がある
- 管理画面(`admin.html`)の「登録ユーザー一覧」の登録日時・最終ログイン日時は、
  `public/admin.js`の`formatDateTime()`で明示的にUTCとしてパースしたうえで、
  `Intl.DateTimeFormat`の`timeZone: "Asia/Tokyo"`を使って常に日本時間(JST)に変換して表示する。
  見出しにも「登録日時(JST)」「最終ログイン日時(JST)」と明記している
- 同様の「DBの生UTC文字列をブラウザのローカルタイムゾーン解釈に依存したまま表示している
  箇所」が他にも残っている可能性がある。見つかった場合は同じ考え方(明示的にUTCとして
  パース→`Asia/Tokyo`へ変換)で対応する

### 「今日」ボタンの日付判定

購入画面(`index.html`)・購入履歴画面(`history.html`)の「今日」ボタン、および購入画面の
初期選択日付は、いずれも共有関数`todayDateKey()`(`public/utils.js`。ローカルタイムゾーン
基準で`YYYY-MM-DD`を組み立てる)を使って「今日」を判定する。`Date.prototype.toISOString()`
(UTC基準)は使わない。**理由**: UTC基準の判定だと、日本(JST=UTC+9)で日付が変わってから
午前9時頃までの間は前日の日付を返してしまい、この時間帯に「今日」ボタンを押すと画面に
よって選択される日付がずれる不具合が起きるため、両画面で判定ロジックを統一している。

### 日付・金額の共通フォーマッタ(`public/utils.js`)

日付表示・金額表示は`public/utils.js`の共通関数に一本化している。`utils.js`は
各画面固有JS(`app.js`・`stats.js`等)より先に読み込まれる構成のため、全画面と
`cart.js`(かご)から同じ実装を参照できる。

| 関数 | 出力例 | 用途 |
|---|---|---|
| `formatDate(dateStr)` | `2026/08/24(日)` | 全画面共通の標準日付表示 |
| `formatDateMdW(dateStr)` | `8/24(日)` | 管理画面「未登録レース一覧」(年を出さない) |
| `formatDateMd(dateStr)` | `8/24` | 集計画面レース別の集計名(年・曜日を出さない) |
| `formatYen(n)` | `¥1,234` | 金額表示。数値以外・nullは0扱い |
| `formatSignedYen(n)` | `+¥1,234` / `¥-500` | 収支など符号付き金額(負号は`¥`の後ろ) |
| `formatSignedNum(n)` | `+1,234` / `-500` | 購入履歴カレンダーの日別収支セル(`¥`なし) |

- 以前は`utils.js`・`prediction.js`・`races.js`・`stats.js`・`admin.js`がそれぞれ
  `formatDate`という同名関数をグローバルスコープに定義しており、HTMLのscript読込順で
  「月日2桁(`08/24`)」と「月日1桁(`8/24`)」のどちらが有効になるかが画面ごとに変わり、
  全画面共通の`cart.js`の日付表示が画面によって揺れていた。月日2桁ゼロ埋めへ統一した
  (2026-09-07)。年なし・曜日なしの表記が必要な画面は`formatDateMdW`/`formatDateMd`を使う
- `admin.js`の`formatDateTime()`(DBの生UTC文字列→JST変換。上記「日時表示のタイムゾーン」)は
  用途が異なるため統合対象外。`admin.js`内に残置

## レスポンシブ対応

- ブレークポイントは3段階: `700px`以下(タブレット〜大きめスマホ)、`600px`以下
  (モバイルヘッダー簡略化)、`430px`以下(iPhone SE3等の小型スマホ)。狭い方のルールは
  広い方のルールに追加で重ねる形で適用される
- **モバイルヘッダー(masthead)**: `600px`以下では「馬券帳」のタイトル表記を非表示にし、
  ナビ(馬券購入・馬券履歴・集計・レース管理・管理)・ユーザー名・退場ボタン等を**すべて
  1つの行**にまとめる。この1行が画面幅に収まりきらない場合は、折り返しではなく**行全体を
  横スクロール**にする。実装は`.masthead-inner`を`display: contents`にし、`.masthead`
  自体に`overflow-x: auto`を指定することで実現している。これは実機のブラウザでURLバーの
  表示/非表示によりヘッダーの見かけの高さがばらつく問題への緩和策であり、ブラウザの
  ネイティブな挙動そのものを完全に制御するものではない
- **購入画面(`index.html`)の組み合わせ選択表**(`.bet-horse-row`): `430px`以下では、馬名を
  折り返さず1行に収め、はみ出した分は省略(`…`)表示にする。チェックボックス/ラジオ欄は
  横並びを維持したまま固定幅で確保し、枠番・馬番の列幅もさらに縮小する
- **予想登録画面(`prediction.html`)の説明文**: `600px`以下では、操作説明(`.prediction-help`)を
