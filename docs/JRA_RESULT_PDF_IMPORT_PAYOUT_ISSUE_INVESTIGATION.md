# JRAレース結果PDFインポート(払戻取込)が0レースになる不具合 調査・修正記録

**ステータス: 0レース問題は実機で解消を確認済み。①②③(騎手・並び順・枠番)も
修正済み(構文チェック・Node単体テスト済み、実機再検証は未実施)。④(払戻の
一部欠落)のみ未解決・追加情報待ち。**

このドキュメントは `docs/JRA_RESULT_PDF_IMPORT_FIX_V3〜V5.md` 等と同様の
「修正記録」。④の解消をもって完了とする(末尾「この調査記録の使い方」参照)。

## 症状(2026-08-05報告)

`races.html` の「JRAレース結果PDFをインポート」から実際のJRA公式サイトの
「レース結果一覧」PDFを取り込むと、解析結果が **0レース** になる。

## 原因(実機診断ログにより確定・2026-08-06)

ユーザーから実ブラウザでの診断パネルの実測値を共有してもらい、原因を確定した。

| 項目 | 実測値 | 意味 |
|---|---|---|
| 抽出行数 | 615 | PDF.js自体のテキスト抽出は正常 |
| 発走時刻候補 | 13 | 「N時M分」パターンは検出できていた |
| 「発走時刻」候補 | **0** | 「発走」+「時刻」という文字列が1件も検出できない |
| 日付候補 | **0** | 「2026年8月2日」のような日付パターンも0件 |
| 開催情報候補 | **0** | 「2回中京4日」のような開催情報パターンも0件 |

「時」「分」のような1〜2文字の隣接パターンは検出できるのに、「発走」「時刻」の
ような**単語をまたぐ文字列**が軒並み検出できていないことから、行内テキストの
連結方法に問題があると特定した。

`public/jra-result-pdf.js` の `jraResultExtractPdfPages()` は、PDF.jsが返す
個々のテキスト断片を同一行(Y座標が近い)ごとにグルーピングしたあと、

```js
text: r.items.sort((a,b)=>a.x-b.x).map(x=>x.str).join("\t"),
```

のように、**間隔の大小を一切見ずに一律タブ文字で連結**していた。JRA公式PDFの
ような表形式で几帳面に組版されたPDFでは、1文字・1単語ごとに別々のテキスト
オブジェクトとして配置されていることが多く、この場合「発」と「走」の間、
「２０２６」と「年」の間のような、**本来隙間なく続く1つの単語の内部**にも
タブが挿入されてしまう。

一方、`jraResultIsStartLabel()`(`発走\s*時刻`)、`jraResultFindMeeting()`
(`(\d{4})年...`、`(\d+)回(競馬場)(\d+)日`)などの正規表現は、文字同士が
隙間なく連続していることを前提に書かれていたため、間にタブが挟まると
軒並み不一致になっていた。時刻検出(`\d{1,2}\s*時\s*\d{1,2}\s*分`)だけは
たまたま全ての区切りに`\s*`を入れていたため、唯一検出できていた。

なお、`docs/JRA_RESULT_PDF_IMPORT_FIX_V3.md`〜`_V5.md`・`_DIAGNOSTIC_V6.md`・
`_VALIDATION.md`に記載された過去の「検証済み」は、実ブラウザのPDF.js抽出結果
ではなく、手作業でシミュレーションしたテキストに対する検証だったため、
この実PDF特有の挙動を見逃していた。

## 修正方針・実装内容(2026-08-06承認・実装済み)

**方針A: 行結合時のタブ一律連結をやめ、実際の間隔(ギャップ)を計測して
「連結/スペース/タブ」の3段階に振り分ける** 方式を採用した(承認済み)。

`jraResultJoinRowItems()` を新設し、直前のテキスト要素の右端から今回の要素の
左端までの実測ギャップを、直前要素の文字幅に対する比率で判定する。

- 隙間がごく小さい(同一単語内の文字とみなせる) → 連結(区切り文字なし)
- 隙間が単語区切り相当 → 半角スペースで連結
- 隙間が列区切り相当(表組みのセル間など) → タブで連結(表構造の解析を維持するため)

これにより「発走時刻」のような単語は正しく1つの文字列として復元され、
`\s*`を使った既存の正規表現もそのまま機能する。表組み(払戻表等)の列区切りは
引き続きタブとして区別されるため、既存の表構造解析ロジックへの影響を避けている。

あわせて、以下の主要な検出関数には**保険として**単語内にも`\s*`を許容する
形に変更した(閾値調整の余地や、フォントによる微妙な間隔差に対する保険)。

- `jraResultParseDate` / `jraResultFindMeeting` / `jraResultFindMeetingLoose`
  (年月日・開催回のパターン)
- `jraResultIsStartLabel`(「発走時刻」)
- `jraResultParseCourseLoose` / `jraResultParseCourse`(「コース」「メートル」)
- ヘッダー復元時の「本賞金」検出

閾値(`JRA_GAP_SPACE_RATIO` / `JRA_GAP_TAB_RATIO` 等)は経験則による仮の値であり、
実機での再検証時にずれが見つかれば調整が必要になる可能性がある。そのため、
診断パネルに新しく「行内文字間隔サンプル・閾値調整用」というセクションを追加し、
各行を構成するテキスト断片間の実測ギャップと、連結/SPACE/TABどれと判定したかを
確認できるようにした(`jraResultRenderDiagnostics()`)。

パーサーバージョンは `7.0.0-diagnostic` → `8.0.0-gapjoin` に更新し、
診断パネルの見出しで区別できるようにした。

## 実機再検証の結果(2026-08-07・解消確認)

修正版で再度PDFインポートを試してもらった結果、以下の通り0レース問題は
解消した。

- 「レース開始検出」「有効レース」: 期待通り12件(修正前は0件)
- 「PARSE DONE headers=12 records=12」

一方で、登録された内容の細部(騎手・出走馬の並び順・枠番・払戻の一部)に
不備が見つかったため、続けて調査・修正した(下記「2026-08-08」の節参照)。

## 今回の修正では対応していない、別件の既知の不具合(未修正)

0レース問題とは独立した問題として、以下2点も調査中に見つかっている。
今回は方針Aの承認範囲(0レース問題の解消)のみを実装しており、以下は
**未修正**。別途承認を得てから対応する。

### (a) `functions/api/races/results-import.js` の払戻マージが「完全に空の場合のみ」しか反映しない

PDFインポート側は常に `mode: "fill-empty"` を送信しているが、
`results-import.js` 側はこのモードで「既存の `payouts` が空でない場合、
新しい解析結果を書き込まない」動作になっている。CSVインポート側にある
`mergePayouts()` のような「式別ごとに追記・上書きする」ロジックが、
PDFインポート側には無い。

### (b) PDF側の払戻金額抽出正規表現が矢印区切り(→)に対応していない可能性

```js
/(\d+(?:\s*[-,、]\s*\d+){0,2})\s+([0-9,]+)\s*円/g
```

組み合わせ番号の区切り文字として `-`・`,`・`、`のみを許容しており、矢印(`→`)に
対応していない。馬単・三連単で該当しうるが未検証。

## 2026-08-08: 実機での12レース解析成功後に判明した個別項目の不備と対応

実機で「headers=12 records=12」となり、主要因(ギャップ結合)の修正が有効であることを
確認できた。一方で、登録内容に以下の不備が報告された。

| 項目 | 状態 | 対応 |
|---|---|---|
| レース管理カレンダー(レース番号・レース名・コース情報) | 正常 | 対応不要 |
| 出走馬表: 騎手が未登録 | 🟢 修正済み | 下記① |
| 出走馬表: 着順順に並んでいる(馬番順であるべき) | 🟢 修正済み | 下記② |
| 出走馬表: 枠番と馬番が一致しない | 🟢 修正済み(要方針確認のうえ実装) | 下記③ |
| 払戻: 複勝(1・3着)、枠連、ワイド(1-2・2-3着)が未取得 | 🟡 未修正(追加情報待ち) | 下記④ |

### ① 騎手が未登録(修正済み)

`jraResultParseHorseFromResultLine()` が馬名・性齢までしか抽出しておらず、
呼び出し側で `jockey:null` を決め打ちしていた(騎手抽出処理自体が未実装だった)。

実データを確認したところ、結果表の各行は
`馬番 馬名 性齢 負担重量 騎手名 タイム 着差 ...` という形式で、騎手名は
「姓 名」の間にスペースが入り、見習い騎手には「▲上里 直汰」のような印が付く。
負担重量の直後・タイム(`M:SS.s`形式)の直前という位置関係を手がかりに
騎手名を切り出す正規表現を追加し、見習い印は表示用に取り除くようにした
(`jraResultCleanJockeyName()`)。

### ② 出走馬が着順順に並ぶ(修正済み)

結果表を上から順に読み取っているため、`current.entries` が着順順のまま
格納されていた。出走馬表編集画面(`races.js`)は「entries配列のi番目 ≒
馬番(i+1)」という前提で行を描画するため、ソートされていない配列を渡すと
表示が総崩れになっていた。各レースの解析完了時に
`current.entries.sort((a,b)=>a.horse_number-b.horse_number)` を追加した。

### ③ 枠番と馬番が一致しない(修正済み・ユーザー承認済みの方針で実装)

実データを確認したところ、**JRAの結果PDFは枠番を色付きアイコンで表現している
ことが多く、結果表の各行にはテキストとして枠番の数字が現れない**ことが判明した
(着順の直後に続く数字は馬番のみ)。

ユーザーとの合意により、**出走頭数から`races.js`の`defaultWakuNumber()`と
全く同じロジックで簡易な初期値を算出する**方針を採用した。②のソート後、
出走頭数(`current.entries.length`)をもとに、枠番が未取得(null)の各出走馬へ
`defaultWakuNumber(馬番, 出走頭数)`を適用する。この関数は`races.js`側の
出走馬表新規登録時の初期値計算と同一ロジックであり、実際の抽選結果とは
異なる可能性がある「目安値」という位置づけも既存のUIと一貫している。

`jra-result-pdf.js`は`races.js`より先に読み込まれるが、`defaultWakuNumber`の
参照自体はPDF解析ボタン押下時(=全スクリプト読み込み完了後)に発生するため、
読み込み順の問題はない(念のため`typeof defaultWakuNumber === "function"`で
存在チェックしたうえで呼び出す)。

**既知の限界**: この頭数は「結果表に登場した出走馬の数」から計算しているため、
除外・出走取消(除外馬)等で結果表に一部の馬が載らないレースでは、実際の
頭数とズレる可能性がある(この場合も既存UIの新規登録時と同程度のリスクであり、
登録後に手動で枠番を修正できる)。

### 単体テストによる検証(Node上でのロジックテスト。実機確認は別途必要)

添付されたPDFと同一ファイルの実テキスト(結果表・払戻表)を使い、
`jraResultParseHorseFromResultLine()`・`jraResultParseExtractedPages()`を
Node上で直接実行して検証した。

- 騎手名抽出: 3件のサンプル行(見習い印付きを含む)すべて正しく抽出できることを確認
- 出走馬の並び順・枠番: 馬番昇順に並び、未取得の枠番に出走頭数ベースの
  初期値が入ることを確認(ただしテストに使った範囲が1レース分の一部ページ
  だけだったため、頭数が過少に計算され末尾の枠番に偏る事象が発生。**これは
  テスト方法上の制約であり、実際のフル解析では同一レースの全ページを
  通して処理するため頭数は正しく計算される**)
- 払戻(複勝・枠連・ワイドを含む全式別): このテキスト形式であれば
  **全項目正しく取得できる**ことを確認

### ④ 払戻の一部欠落(複勝1・3着、枠連、ワイド1-2/2-3着) — 未修正・追加情報待ち

上記の単体テストで、複勝・枠連・ワイドを含む全ての払戻がこのテキスト形式では
正しく取得できることを確認したため、**コードのロジック自体に明白な欠陥は
見当たらない**。実際のブラウザでの前回実行時(2026-08-07、パーサー
`8.0.0-gapjoin`)にこの部分だけ取得できなかった理由は、実PDF.jsのギャップ
判定がこの単体テストで使ったテキストと異なる行分割を生んだ可能性が高いが、
実機の生テキストを確認しない限り断定できない。

**次回インポート時にお願いしたいこと**: 診断パネルの「PDF全文抽出テキストを
表示」から、複勝・枠連・ワイドの払戻表部分に該当する行(該当レース1つ分で
可)を共有してもらえれば、原因を確定して対応する。

### ③ 追記(2026-08-09): 枠番の算出ロジックが逆だったため修正

実機で①②③修正版を試したところ、騎手名は正しく取得できたが、**枠番の算出が
実際のJRAの傾向と逆になっている**との指摘を受けた(例: 18頭立てで1・2枠が3頭に
なってしまう。実際は7・8枠側に余りが寄るべき)。

原因は`races.js`の`defaultWakuNumber()`自体のバグだった(PDFインポートの③修正は
この関数をそのまま再利用していたため、同じ誤りを引き継いでいた)。

```js
// 修正前: 余りを若い枠(1,2...)に寄せてしまっていた
const size = waku <= remainder ? base + 1 : base;

// 修正後: 余りを大きい枠(7,8...)に寄せる(JRAの実際の傾向と一致)
const size = waku > (8 - remainder) ? base + 1 : base;
```

Node上で9・11・16・18頭のケースを検算し、修正後は以下の通り実際のJRAの
傾向(9頭立ては8枠に2頭、18頭立ては7・8枠に3頭など)と一致することを確認した。

| 頭数 | 修正前の分布 | 修正後の分布 |
|---|---|---|
| 9頭 | 1枠に2頭、2〜8枠は1頭ずつ | 8枠に2頭、1〜7枠は1頭ずつ |
| 11頭 | 1〜3枠が2頭、4〜8枠が1頭 | 6〜8枠が2頭、1〜5枠が1頭 |
| 18頭 | 1・2枠が3頭、3〜8枠が2頭 | 7・8枠が3頭、1〜6枠が2頭 |

この関数は`races.js`側の「出走頭数を選ぶと枠番の初期値が自動入力される」機能
(新規レース登録時)とも共通のため、**この修正によりPDFインポート経由だけでなく
通常のレース新規登録時の枠番初期値も正しくなる**。
