**フェーズ12(CSV取込履歴が表示されなくなる障害の修正)**
- 症状: CSVインポート中に「Too many API requests by single Worker invocation」
  エラーが発生し、以降`GET /api/ticket-imports`が500エラーとなってインポート履歴が
  画面に一切表示されなくなった
- 原因: `functions/api/ticket-imports/index.js`が典型的なN+1クエリになっていた
  - `GET`: `imported_ticket_groups`を取得後、**グループごとに**`imported_ticket_items`を
    個別クエリしており、取込件数(グループ数)が増えるほどD1への問い合わせ回数が増加。
    Cloudflare Workersの1リクエストあたりのサブリクエスト数上限に達し500エラーになっていた
  - `POST`(CSV取込本体): CSVの**行ごとに**「既存重複チェック」「レース参照(SELECT/INSERT)」
    「重複候補検出」を個別クエリしており、行数の多いCSVを取り込むと同じ上限に抵触していた
    (このPOST側の失敗が、添付画像1枚目のエラーの直接の発生源とみられる)
- 対応:
  - `GET`: グループを取得後、`imported_ticket_items`は全件を1回のクエリでまとめて取得し、
    メモリ上でグループごとに振り分ける方式に変更(クエリ回数がグループ数に依存しない定数回に)
  - `POST`: 既存重複チェック用のキーをリクエスト開始時に1回だけ取得してメモリ上で照合、
    レース参照は行内でキャッシュして同一レースへの再問い合わせを回避、重複候補検出は
    全行の取込完了後に1回のクエリでまとめて行うよう変更(1行あたりのクエリ回数を削減)
  - Node.js標準の`node:sqlite`でD1互換のモック(`prepare/bind/first/all/run/batch`)を作り、
    実際にCSV取込→一覧取得→同一ファイル再取込時の重複スキップ→着順/払戻のレース反映、
    までを動作確認済み(30行/6レースのCSVで、`GET`のクエリ回数はグループ数によらず3回、
    `POST`のクエリ回数も従来実装比で大幅に削減されることを確認)
- 既知の限界: CSVの行数が非常に多い場合(数百行規模)は、行ごとに発生する書き込み系クエリ
  (取込元行・グループ・レース更新など)自体は削減しきれておらず、依然として上限に達する
  可能性が残る。再発する場合はCSVを分割して取り込む、または書き込みも`db.batch()`で
  まとめて1リクエスト化するさらなる改修を検討する

**フェーズ15追記2(latest1.sqlの安全な再実行・2026-08-03)**
- 「`schema.sql`=まっさらな状態から1回、`latest1.sql`=以降は毎回これだけ実行すれば
  最新化できる」という運用条件を明確化する指摘を受け、`scripts/migrate.js`を新設。
  SQLiteには`ADD COLUMN IF NOT EXISTS`が無いため、`latest1.sql`を素の`--file=`で
  まるごと再実行すると(a)列の重複追加でエラーになる、(b)v13のテーブル再構築
  ブロックが再実行されて`user_id`が`NULL`に巻き戻る、という2つの問題があることが
  判明(bは特に無言のデータ破壊で危険)。ローカルDBで実際に「初回実行→データ投入→
  再実行」を検証し、対策前は`user_id`が巻き戻ることを確認した上で、
  `scripts/migrate.js`(`prediction_marks.user_id`の有無で危険区間をスキップ+
  安全区間は既知の「適用済み」エラーのみスキップ)を実装。再実行してもデータが
  保持されることを検証済み。以後は`node scripts/migrate.js --remote`(または
  `--local`)を実行すればよい運用にした。READMEも更新
- 実際に`--remote`で実行したところ、v13適用済みにもかかわらず「未適用」と誤判定され、
  `duplicate column name: user_id`でエラーになる不具合が発覚。原因は`--remote`実行時に
  wranglerが出す`Uploading...`等の進捗メッセージがJSON結果の前に混ざり、判定用の
  `JSON.parse`が失敗していたこと。「最初の`[`以降だけを抽出してからパースする」よう修正し、
  加えて**判定に失敗した場合は「未適用」と早合点せず、安全側に倒して処理を中断する**よう
  変更(誤って危険区間を実行しデータを壊すことを防ぐため)。ローカルで初回適用・冪等性
  (2回目以降の全スキップ)とも再検証済み
- 「初期セットアップ以外は`latest1.sql`を意識せず`migrate.js`を実行するだけでよい」
  「本番は運用中のためテーブル・データを削除する変更は極力行わず、必要な場合は
  必ず承認を得る」という運用ルールをREADME・DESIGN.mdに明記

## 複数ユーザー対応 確定仕様(2026-08-01)

目的: 家族それぞれが個別のログインID/パスワードを持ち、購入履歴・インポート履歴・
予想印/メモを完全に分離して管理できるようにする(近い将来の利用を見据えた対応。
まず2人分から開始し、将来的に人数が増える想定)。

確定した仕様:

- 認証方式: 家族それぞれに個別のログインID/パスワードを持たせる(現状の「全員共通の
  1つのパスワード」から廃止)。ログイン画面はユーザー名(テキスト入力)+パスワードの
  2項目に変更する
- データの可視性: 各ユーザーの購入履歴・インポート履歴・予想印・メモは完全に別々とし、
  他のユーザーからは見えないようにする(世帯合算ビューは不要)
- レース情報(races: 日付・競馬場・出走馬・着順・払戻など)は実世界の共通データであり、
  ユーザーごとに分ける対象ではない(全ユーザーで共有)。分離が必要なのは「誰が何を買ったか
  (tickets/imported_tickets/imported_ticket_groups/imported_ticket_items)」
  「誰の予想印・メモか(prediction_marks/prediction_notes/horse_notes)」の部分
- **レース情報の登録・編集(レース登録・出走馬表・着順・払戻の入力/編集、開催日程の
  一括登録)は管理者のみ**が行える。一般ユーザーはレース情報を閲覧・参照するのみ
- **CSVインポート時の自動レース登録は廃止する**。現状`functions/api/ticket-imports/index.js`
  のPOSTは、該当レースが`races`に無ければ自動的に新規作成しているが、レース登録が
  管理者限定になったことに伴い、この自動作成処理は削除する。該当レースが未登録のまま
  CSVを取り込んだ場合は`race_id`をnullのまま(日付・競馬場・レース番号・レース名は
  取込グループ側にそのまま保持)にしておき、後日管理者がそのレースを登録した際に
  紐付けられるようにする(既存のバックフィル的な仕組みを流用・拡張できないか、
  実装時に確認する)
- 「所有者を変更」する機能は**不要**(導入後は新規データが自動的にログインユーザーへ
  正しく紐づくため、後から変更する必要がない)。既存データ(個別ログイン導入前の
  購入履歴・インポート履歴)は、一括で代表ユーザー(管理者アカウント)に割り当てる
  だけでよい
- ユーザー登録: **ログイン画面に「新規ユーザー登録」を用意し、誰でもユーザー名(ID)と
  パスワードを自分で指定してその場でアカウント作成できる**(管理者による承認・招待コードは
  無し。アプリのURLを知っている前提でオープンに登録可能とする)
- 管理者判定: **Cloudflare Pagesの環境変数`ADMIN_USERNAMES`(カンマ区切り)に含まれる
  ユーザー名でログインした人だけが管理者として扱う**。DBに管理者フラグは持たせない
  (誤って書き換わるリスクがなく、環境変数を編集するだけで管理者を増減できるため)。
  最初の管理者は「先に通常のユーザー登録を行う→そのユーザー名を`ADMIN_USERNAMES`に
  追加する」という順番で設定する(鶏と卵の問題は発生しない)
- ユーザー削除機能: **今回は実装しない**(優先度低・将来必要になれば追加検討。実装コスト次第)
- パスワードを忘れた場合の救済措置(パスワードリセット等)は**今回は実装しない**。
  将来のタスクとして別途記録する(下記「未着手タスク一覧」参照)
- **管理者向け画面(2026-08-01追加・スコープに含める)**:
  1. **未登録レース一覧**: CSVインポートの自動レース登録を廃止したことに伴い、「CSVで取り込まれたが
     まだ`races`に登録されていない日付・競馬場・レース番号」の一覧を管理者向けに表示する。
     `imported_ticket_groups`のうち`race_id IS NULL`のものを日付・競馬場・レース番号でグルーピングして
     一覧化し、そこからレース登録画面へワンクリックで遷移できるようにする(遷移先で日付・競馬場・
     レース番号を事前入力しておくと親切)
  2. **登録ユーザー一覧**: `users`テーブルのユーザー名・登録日時を一覧表示する、管理者向けの
     閲覧専用画面(編集・削除機能は無し)。オープン登録(招待コード無し)のため、管理者が
     誰が登録したかを把握できるようにする目的

現状把握(2026-08-01時点のコード調査):

- 現在の認証はfunctions/_middleware.js + functions/api/auth/login.jsによる、
  環境変数APP_PASSWORDと照合するだけの全員共通パスワード方式。セッションCookieには
  有効期限(exp)のみが入っており、ユーザーを区別する情報は一切持っていない
- tickets・imported_tickets・imported_ticket_groups・imported_ticket_items・
  prediction_notes・prediction_marks・horse_notesのいずれのテーブルにも、
  所有者を表すカラムは存在しない

実装時の主な変更点(見積り・大規模になる想定):

1. usersテーブルを新設(id, username, password_hash, created_at)。管理者フラグはDBに
   持たせない(環境変数ADMIN_USERNAMESで判定するため)。パスワードはcrypto.subtleの
   PBKDF2等でハッシュ化して保存する
2. ログイン画面をパスワードのみ→ユーザー名+パスワードの入力に変更し、「新規ユーザー登録」
   導線を追加する。functions/api/auth/login.jsはusersテーブルと照合する方式に変更し、
   functions/api/auth/register.js(新規)でアカウント作成(作成後は自動ログイン)を行う
3. セッションCookieのペイロードにuser_id・usernameを含めるように変更し、
   functions/_middleware.jsで検証後、context.data.userId・context.data.isAdmin
   (ADMIN_USERNAMESとの突合結果)として後続のハンドラに渡す
4. tickets・imported_tickets・imported_ticket_groups・imported_ticket_items・
   prediction_notes・prediction_marks・horse_notesにuser_idカラムを追加する
   マイグレーション(schema.sql・latest*.sql・実データ移行スクリプトの3点が必要)。
   移行スクリプト自体では既存行のuser_idはNULLのままとし、管理者アカウント作成後に
   別途「既存データを管理者に割り当てる」SQLを1回実行する運用とする
5. 上記テーブルを読み書きするすべてのAPIエンドポイント(tickets、ticket-imports、
   prediction-notes、prediction-marks、horse-notes、stats集計まわり)に
   WHERE user_id = ?のフィルタ、および新規作成時のuser_idセットを追加する
   (touch pointが多いため、影響範囲の洗い出しに時間をかけて着手する)
6. races関連のAPI(レース登録・編集・出走馬表登録・払戻登録・開催日程一括登録・削除)に
   管理者権限チェック(context.data.isAdmin)を追加する
7. functions/api/ticket-imports/index.jsの「該当レースが無ければ自動作成する」処理を削除する
8. 管理者向け画面を新設: 「未登録レース一覧」(race_id未紐付けの取込グループをレース単位で
   集計して表示)、「登録ユーザー一覧」(users一覧の閲覧のみ)
9. 上記「馬券かご」機能と組み合わせる場合、localStorageのキーをユーザーごとに分ける


## リファクタリング候補(2026-08-04提案)のうち実装済み分の詳細

### 候補1(最小): 共通ユーティリティ関数の重複統合 **実装済み(2026-08-04)**
- `escapeHtml`が`admin.js`・`prediction.js`・`races.js`・`stats.js`にそれぞれ個別実装されていた。
  `escapeAttr`も`prediction.js`・`races.js`に個別実装があった

  読み込んでいたのは`buy.html`・`index.html`のみで、`admin.html`・`prediction.html`・
  `races.html`・`stats.html`には`<script src="utils.js">`自体が無かった
- **対応内容**: 上記4画面のHTMLに`<script src="utils.js">`を追加(既存の`buy.html`/
  `index.html`と同じ並び順=他スクリプトより先に読み込む)し、各JSファイル内の重複定義
  (`escapeHtml`/`escapeAttr`)を削除して`utils.js`版に統一した。`utils.js`版は
  `str ?? ""`でnull安全なため、削除前の各ファイルの呼び出し箇所(渡す値は全て文字列 or
  条件式で空文字にフォールバック済み)への影響は無い

  今回は統合していない

### 候補3(小): CSVインポートのエラーハンドリング追加 **実装済み(2026-08-04)**
- `imported_ticket_groups`のUNIQUE制約(`uq_imported_group_source_key`)違反時に、以前は
  リクエスト全体が500エラーで中断していた
- **対応内容**: `functions/api/ticket-imports/index.js`の該当INSERT文をtry/catchで囲み、

  `continue`で次の行の処理へ進めるように変更(他の想定外エラーは従来通り500として扱う)。
  レスポンスに`conflicted`/`conflicts`を追加し、`public/app.js`のCSVインポート結果アラートに
  「◯件は別のユーザーが登録済みのデータと衝突したため取り込めませんでした。」という
  案内を追加した
